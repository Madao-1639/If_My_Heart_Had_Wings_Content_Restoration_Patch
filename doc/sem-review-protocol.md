# 逐行通读评审协议

给「中文成品逐行通读」评审执行者（subagent 或人工）的判定与交付规则。提案与凭证都是过程稿，留在 `tmp/`；通过机检的条目按槽位**增量并入**改动表 `resource/corpus/review_fixes.jsonl`（`from` 记 `pin_zsweep`）。`script/corpus/merge_fixes.py` 的全表重建要求语境层源层齐备，缺源层即拒写，因此新一轮不走全表重建。

## 1. 证据文件读法

- `idxNN` 单独一行是槽位号；紧随的 `J: ` 是日文原文，`C: ` 是当前中文成品。
- `@ 日文名 → 中文名` 是说话人映射，不是槽位，不得为它写提案。
- 必须整批读完，禁止抽样后就下结论。

## 2. 只报「该行自身有硬伤」

issue 取值固定为 `meaning` / `omission` / `name` / `number` / `typo` / `untranslated`：

| issue | 判定 |
|---|---|
| meaning | 意思反了或读不通：反义、肯否颠倒、主客颠倒、已然/未然颠倒 |
| omission | 日文实义成分整块丢失，中文缺谓语或缺关键信息 |
| name | 人名/专名错字或张冠李戴（如 亜紗 写成别的字、佳奈子 写成形近字） |
| number | 数字、数量、方位（里/后、上/下）错 |
| typo | 错字漏字导致不成句 |
| untranslated | 日文汉字词直接留在中文里（如 部活、通学路） |

**不报**（属译风，不是缺陷；批量统一它们会造成回归）：

- 同一日文假名词/拟声词的多种中文写法（ぎゅっ→紧抱 vs 啾；れろ→咧咯 vs 舔舔）。
- 语气词选择（恩/嗯、哪/呢、啊/呀）。
- 敬称风格与「同学/姐姐」一类的可通变体。
- 语义可通的近义意译、跨行的行文统一诉求。

宁缺毋滥：一处近义偏差不算缺陷，只有该行读不通或与日文事实相反才报。

## 3. cn 字段的硬约束

`cn` 必须是**整行**译文，且与该行 `C:` 满足：

1. `%K` / `%P` 序列与顺序完全相同（不多、不少、不换位）——这决定台词翻页节奏。
2. 字面 `\n`（**单个**反斜杠 + 字母 n，两个字符）个数相同，每个 `\n` 后的全角空格缩进照抄。
   说的是 `cn` **解码后的值**，所以 JSON 源文件里要写 `\\n`；直接写 `"\n"` 是 JSON 转义，解码出来是**真换行字符**，一样会把软换行结构打烂（机检报 `softbreak-mismatch`）。
   写成 `\\n`（双反斜杠）里仍然含有一个 `\n`，光数个数发现不了，但游戏会原样显示反斜杠，一律判废。
3. `「」` 数量相同；不得新增 `（）` 解说括注；不得残留假名。
4. 只改硬伤，其余文字尽量不动。

## 4. quote 与 note

- `quote`：从该行 `J:` 日文里**原样连续复制** 5–20 字。机检会断言它逐字出现在日文侧，这是防"凭印象改译文"的证据链，臆造即作废。
- `note`：一句中文，说明对应哪段日文、错在哪。

## 5. 交付

- 用 Write 输出 `tmp/corpus_review/sem_{SCRIPT}_{NN}.jsonl`，UTF-8，一行一条 JSON，无数组包裹、无尾随空行；字段顺序 `script` / `idx` / `cn` / `quote` / `issue` / `note`。
- `script` 是槽位所属脚本名（如 `AGE_001`），`idx` 是整数。
- 动笔前先确认该批文件不存在：一个批次同一时刻只允许一个评审者，已存在即回报冲突并停笔、**禁止覆盖**。
- 全批无硬伤时写 0 行空文件并如实说明，不得为凑数造提案。
- 写完必须 Read 回读确认落盘且每行合法 JSON。
- 禁止修改任何其它文件；禁止推测构建/校验流水线内部机制。读不到文件、看不懂某行、时间不够时直接回报「未完成」及原因，禁止编造槽位号或译文。

## 6. 机检与落地（主 agent 侧，评审者无需执行）

提案机检逐条断言，任一不过即拒收该条：

- 反幻觉两道：`idx` 属于该批次证据文件（`idx-not-in-batch`）、`quote` 逐字出现在该行日文里（`quote-not-in-jp`）。
- 结构四条：`%K`/`%P` 序列、字面 `\n` 个数、`「」` 数量、不新增括注。
- 译文合法：非空、无残留假名、含汉字、不照抄日文、与现文有差异。

落地是**按槽位增量并入**改动表 `resource/corpus/review_fixes.jsonl`（`from: pin_zsweep`）。已写进改动表 `pin_zsweep` 层的条目在"与现文无差异"这条判据上豁免——判据基线是成品，成品重建后已含提案文本，不豁免会把已落地的条目全部误判成废话而拒掉。

交付核对管「有没有读到末尾」，**单薄度核对**管「读了但没报」：按每百槽提案数对比全语料中位数，命中率低于中位数一半、或满百槽却 0 提案的批次列为复派优先队列。单薄度只能识别**可疑**，不等于证明漏读——有些批次本来就干净。

**成品重建之后必须重切批次证据文件**：证据文件的 `C:` 取自成品，不刷新会让评审对着旧译文提案。派发前的断言是「逐行核对证据文件 `C:` 与当前成品，不一致行数必须为 0」。
