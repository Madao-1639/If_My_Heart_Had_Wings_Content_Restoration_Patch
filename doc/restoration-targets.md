# 还原目标

## 项目目的

为 Steam 版《在这苍穹展翅》（If My Heart Had Wings）制作内容还原补丁，恢复被 Steam 版删除的原版内容，同时：

1. 保留 Steam 成就系统
2. 恢复完整被删内容
3. 零破坏性修改（不替换 Steam 原有资源）

## 素材来源

| 用途 | 路径 | 性质 |
|---|---|---|
| Steam 版基线（只读参考） | `backup/` | Steam 阉割版官方文件 |
| 原版素材 | `D:\My_Code\tmp\GamePatch\If_My_Heart_Had_Wings\在这片天空下展开一双翅膀(羽翼汉化版V1.0beta2)` | 含完整未阉割剧情脚本、立绘差分、可执行文件（`AdvHD.exe`），另附独立的中文汉化补丁目录（`补丁/`），本身也是一次汉化组的再打包，游戏本体内容与官方原版一致 |
| 英文重翻补丁 | `imhhw_retranslation_patch_v1.1.0.59/` | 全档替换式重翻补丁，额外的 `Chip+.arc`/`Voice+.arc` 仅含 UI 图形微调和 3 条语音修复，不含内容还原 |
| 中文翻译语料参考 | `oozora_CHSpatch/` | 汉化组制作的文本翻译语料与加载器代码，用途已确认符合发布方条款 |

## 已确认的删减范围（截至本次调查）

以下发现均来自直接对比 Steam 版与原版发行版归档的实测结果，不是推测。

### 1. 完全缺失的脚本文件（5 个）

Steam 版 `Rio.arc` 中完全不存在，原版存在：`ASA_002.ws2`、`ASA_004.ws2`、`YOR_003.ws2`、`YOR_005.ws2`、`YOR_007.ws2`。已解码并提取日文文本确认——`ASA_002.ws2` 与 `ASA_004.ws2` 是亚纪线的明确性描写场景（角色"亜紗ちゃん"），`YOR_003.ws2` 是依瑠线的明确性描写场景（角色"依瑠ちゃん"），均为 H 场景对白，不是普通剧情或日常对白。Steam 版通过**直接改写前后脚本的跳转目标**把这些场景整段跳过（例如 `ASA_001.ws2` 原版结尾跳转到 `ASA_002`，Steam 版改为直接跳转到 `ASA_003`），而不是保留一个阉割版脚本占位。

### 2. 脚本内容原地删减（至少 10 个，很可能更多）

比 Steam 版删除整个文件更常见的模式：脚本文件本身在两个版本中都存在、入口和出口跳转目标也相同，但脚本内部的对白/演出内容被原地删减。已确认的显著案例（原版解码长度比 Steam 版长出 5000 字节以上）：

| 脚本 | 原版比 Steam 版多出的字节数 |
|---|---|
| AGE_010.ws2 | 91,160 |
| AGE_007.ws2 | 66,850 |
| KOT_009.ws2 | 42,559 |
| AMA_010.ws2 | 42,340 |
| AMA_006.ws2 | 39,948 |
| AGE_005.ws2 | 36,212 |
| KOT_003.ws2 | 35,074 |
| AMA_004.ws2 | 34,761 |
| KOT_006.ws2 | 21,875 |
| AMA_007.ws2 | 20,150 |

已验证 `AGE_010.ws2`：两版脚本开头、结尾（都跳转到 `AGE_011`）完全一致，中间一段成人向对白被整段删除，脚本文件本身继续存在于调用链中。

**这意味着仅靠"脚本文件是否存在"做调用链审计会漏掉这一类删减**——必须额外做逐脚本的解码长度对比（如上表方法）或逐场景对白比对，才能发现这类"文件存在但内容被抠空"的情况。上表只统计了差值超过 5000 字节的案例，未做完整穷尽扫描，实际受影响的脚本数量可能更多，尤其是差值较小、容易被忽略的场景。

#### 台词级删减验证（基于 Steam 中文版 lng 文件对比）

通过对比原版脚本中的对白条目（按 `lng_idx` 索引）与 Steam 中文版 lng 文件，可以从**台词级别**验证删减范围。已确认存在 lng 文件的 95 个脚本中：

**删减最严重的脚本（lng 匹配率 <60%）**：

| 脚本 | 原版对白数 | lng 匹配率 | 备注 |
|------|-----------|----------|------|
| KOT_009.ws2 | 1116 条 | 38.0% | 原版比 Steam 版多 42,559 字节 |
| KOT_003.ws2 | 1774 条 | 47.0% | 原版比 Steam 版多 35,074 字节 |
| KOT_006.ws2 | 1294 条 | 50.0% | 原版比 Steam 版多 21,875 字节 |
| CO2_999.ws2 | 53 条 | 50.9% | 小场景，但删减比例高 |

**中度删减的脚本（lng 匹配率 60-75%）**：

| 脚本 | 原版对白数 | lng 匹配率 | 备注 |
|------|-----------|----------|------|
| CO1_020.ws2 | 134 条 | 63.4% | - |
| KOT_004.ws2 | 1030 条 | 64.3% | - |
| CO1_017.ws2 | 747 条 | 66.8% | - |
| KOT_005.ws2 | 556 条 | 68.3% | - |
| KOT_008.ws2 | 1497 条 | 71.1% | - |
| CO2_001.ws2 | 137 条 | 71.5% | - |
| CO1_018_E.ws2 | 401 条 | 71.6% | - |
| YOR_004.ws2 | 847 条 | 73.7% | - |
| KOT_002.ws2 | 1011 条 | 73.8% | - |
| CO2_005_B.ws2 | 160 条 | 73.1% | - |

**匹配率说明**：
- 匹配率 = (Steam lng 中存在对应译文的对白数) / (原版脚本总对白数)
- 匹配率低意味着原版包含大量 Steam 版不存在的对白，即被删减内容
- 整体统计：95 个脚本共 49,186 条对白，匹配率 72.0%（35,416 条匹配，13,770 条未匹配）

**验证方法**：
1. 从原版脚本提取所有对话行（`\x14 <idx:u16> ... char\x00 <文本> %K/%P`）
2. 解析 Steam 中文版 lng 文件（XOR 0xCE 解密）
3. 按 `lng_idx` 查找对应关系，统计匹配率

详见 `tool/extract_script_text.py` 和 `tool/merge_translations.py`。

### 3. 立绘/CG 差分资源缺失

已确认多个角色差分目录整批缺失：`CHIP2.arc`（AGE 角色）原版比 Steam 版多 305 个差分文件，`CHIP3.arc`（HUT 角色）多 366 个，`CHIP6.arc`（AMA 角色）多 239 个。命名格式为 `<角色代码>_<场景编号>_<差分编号><B/S>.png`。

### 4. 同名资源内容不同（真实存在的冲突）

已用 SHA256 逐一验证：`CHIP3.arc` 中至少 7 个同名文件（如 `HUT_01_001b.png`），Steam 版与原版字节内容不同、文件大小有数十 KB 差异，怀疑是局部裁剪/遮罩编辑而非整图替换。这确认了"同名不代表同内容"这一类冲突在本项目中真实存在，替换/合并资源时必须逐一核实 hash，不能只看文件名判断是否需要处理。

### 5. `.MOS` 马赛克变体整批缺失

原版部分立绘目录中，每个 `.png` 旁存在一个同名 `.MOS` 变体（已确认是马赛克遮罩版，本身也是合法 PNG，但体积明显更小）。已确认 Steam 版 `CHIP3.arc`、`CHIP6.arc` 中 `.MOS` 文件被整批移除（数量为 0），属于 Steam 版删减范围的一部分。已对全部脚本做完整扫描确认：脚本从未直接引用 `.MOS` 扩展名，一律用 `.PNG` 引用同一 stem，说明 `.MOS`/`.PNG` 的切换由引擎在加载时自行决定，不是脚本层面的选择——具体触发条件尚不明确，见 [engine-mechanics.md](engine-mechanics.md)。

若还原范围涉及原版中存在 `.MOS` 变体的立绘，需要决定是否要一并带回 `.MOS`（还原引擎的马赛克切换行为）还是只带回清晰版 `.png`（取决于是否需要还原游戏原有的审查开关功能，目前尚未确定该功能触发条件，见上）。

### 6. `RIO/SL_*.ws2` 后日谈内容（回想模式专属，低优先级）✅ 内容定性已确认 / ⚠️ 还原方式待调查

原版 `RIO/` 目录下 `SL_AGE_001.ws2`、`SL_AMA_001.ws2`、`SL_HUT_001.ws2`、`SL_KOT_001.ws2` 四个脚本，已确认是四条线（AGE/AMA/HUT/KOT）各自的**后日谈**内容，通过游戏内的**回想模式**（回想/CG 鉴赏一类的二级菜单）进入，不在主线调用链的跳转路径中。

**补充确认**：已用 `tool/arcbuild.py` 读取原版 `Rio.arc` 的完整成员表（161 个成员）逐一核对，这四个 `SL_*.ws2` 文件**均不在 `Rio.arc` 归档内**，只以裸文件形式存在于磁盘上的 `RIO/` 目录中。也就是说，这四个脚本不是"打包进主归档但调用链不可达"，而是压根没有被打包——进一步支持"仅通过回想模式的独立加载路径进入，不经过主线 `Rio.arc` 调用链"这一判断。

Steam 版疑似**整体缺少回想模式入口**（尚未在 Steam 版 `Rio.arc` 或菜单资源中找到对应内容，待逐一核实）。若确实缺少，还原这四个脚本不仅要恢复脚本本身，还要还原回想模式的入口 UI、菜单跳转逻辑，以及引擎识别"何时允许进入回想模式/回想哪些内容"的机制——具体识别机制见 [engine-mechanics.md](engine-mechanics.md) 中的待确认项。

**优先级判断**：相比主线内容删减（第 1、2 节），还原难度明显更高（涉及菜单系统重建而非单纯脚本/资源插入），因此在制定还原范围时**优先级较低**，留待主线还原工作完成后再评估。

### 7. `RIO/` 目录下与 `Rio.arc` 重名的裸文件（疑似构建残留，非还原目标）⚠️ 部分确认

原版 `RIO/` 目录除上述 4 个 `SL_*.ws2` 外，还存在 7 个与 `Rio.arc` 内归档成员同名的裸文件：`CO1_001.ws2`、`CO1_002.ws2`、`CO1_003.ws2`、`CO1_015.ws2`、`HUT_004.ws2`、`HUT_005.ws2`、`start.ws2`。已逐一解码对比这 7 个裸文件与 `Rio.arc` 内同名成员：

- **不是字节级完全一致**（与"同名内容也相同"的朴素假设相反）。
- `CO1_001/002/003/015.ws2`：仅有 1~2 处单字节差异，均出现在形如 `...ffect0X\x00\x00\x00<02 或 00>\x00\x00Wst0X\x00\x00` 的数值字段（疑似某个特效/演出开关标志位），裸文件版本为 `\x02`，`Rio.arc` 内版本为 `\x00`，其余字节完全一致。
- `HUT_005.ws2`：仅 2 处字节差异，落在一段对白的 Shift-JIS 文本内部（`見当は付いい` 类似措辞的微调），推测是同一句对白的不同修订版本。
- `HUT_004.ws2`：解码后长度相差 42 字节（裸文件更短），且从首个分歧点起，用滑动窗口在另一侧未能重新对齐（不是简单的插入/删除，中间内容本身发生了替换）——**这一处尚未查明具体差异内容，需要后续针对性 diff**。
- `start.ws2`：裸文件比 `Rio.arc` 内版本多出约 4 字节的一小段指令（`\xfb\x01\x0b\xe8\x03\x01`/结尾多一个 `\xfc\x01\x00`），疑似菜单/开场跳转逻辑的早期版本差异。

**判断**：这些裸文件很可能是原版发行包构建过程中残留的旧版本/中间版本脚本（例如打包前的暂存目录），不是需要额外还原的被删内容——它们的功能已经被 `Rio.arc` 内的同名成员覆盖，且游戏调用链走的是归档内版本（见第 8 节引擎识别机制的静态分析结果）。**不建议**将这 7 个裸文件视为还原素材来源；若后续要精确核实两者在游玩体验上是否有实质差异（尤其是 `HUT_004.ws2` 的未对齐差异),应以 `Rio.arc` 内版本为准。

### 8. 引擎如何识别 `RIO/` 目录内容 ⚠️ 静态分析结论，未做运行时验证

对 `AdvHD.exe`、`AdvHD.dll` 做过 ASCII 与 UTF-16LE 宽字符串的完整扫描（搜索包含 `RIO`、`.ARC`、`.WS2`、`SCRIPT` 的片段），结果：

- `AdvHD.exe` 中只找到 `Rio.arc`（归档文件名本身）和通用的 `.ws2` 扩展名字符串，**没有**找到任何形如目录扫描路径、"loose override"、调试模式加载裸文件之类的字符串。
- `AdvPatch.dll` 中出现的 `a0RiO` 是二进制数据段里的偶然字节序列（前后是无规律的二进制噪声，不是以 NUL 结尾的独立字符串常量），不能作为"引擎识别 RIO 裸文件目录"的证据。
- 没有找到任何证据表明引擎会在运行时扫描磁盘上的 `RIO/` 裸文件目录并替代/补充 `Rio.arc` 归档内容。

**结论（待运行时验证）**：现有静态字符串证据倾向于支持"引擎只从 `Rio.arc` 归档加载剧本脚本，磁盘上的裸 `RIO/` 目录本身不会被引擎读取"这一判断，裸目录更可能是发行包制作过程中留下的构建残留（原始素材/打包前暂存），而不是游戏运行时依赖的一部分。但这只是字符串级静态分析的结论，没有做运行时验证（如临时改名/删除 `RIO/` 目录后实机测试是否有任何行为变化），也没有对归档加载代码路径做反汇编级核实，**严格来说不能排除存在某种未通过字符串暴露的加载逻辑**。如果后续还原工作依赖对这一结论的高置信度判断，应补做一次实机 A/B 测试。
