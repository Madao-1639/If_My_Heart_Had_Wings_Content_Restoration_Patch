# 引擎机制

本文档记录游戏引擎在运行时表现出的行为规律，区别于 [file-formats.md](file-formats.md) 记录的静态文件格式。可执行文件 `AdvHD.exe`/`AdvHD.dll` 存在于原版发行版目录中（见 [restoration-targets.md](restoration-targets.md)），必要时可用于运行时验证或静态逆向。

## 资源槏位命名 ❓ 待验证

已从脚本内容中观察到的槏位名包括 `st01`、`bg01`（见 file-formats.md 中 LAYER_ORDER 表的例子），但尚未确认：
- 完整的槏位白名单（有多少个 st/bg 槏位，是否有 ev 类事件专属槏位）
- 是否存在对特定槏位的资源名长度/前缀限制

**方法论**：若后续需要给某个资源命名空间加前缀做隔离处理，遇到某个槏位拒绝识别该资源时，优先用 A/B 测试（换成一个不带前缀但等长的新名字，看是否成功）来定性问题，而不是纯静态逆向猜测。

## 资源缺失时的运行时行为 ❓ 待验证

尚未故意构造缺失资源的测试用例来观察引擎实际反应（卡死/报错/静默容忍）。这是排查"游戏卡死无响应"或"画面显示异常但无报错"类问题时需要提前摸清的行为基线，建议在开始改写脚本前先做一次故意的资源缺失测试。

## `.MOS` 马赛克变体的选用机制 ⚠️ 身份已确认，触发条件待调查

已在 [file-formats.md](file-formats.md) 中确认 `.MOS` 是与部分立绘同名的马赛克遮罩变体文件（本身也是合法 PNG，但分辨率/文件大小明显更小）。已确认脚本内容中不包含对 `.MOS` 扩展名的直接引用，说明选用逻辑在引擎内部而非脚本层。需要通过运行时观察（例如切换游戏内的"隐藏敏感画面"设置项，若存在）或对 `AdvHD.exe` 做针对性逆向来确认触发条件。

## 成就系统钩子机制 ✅ 已确认（脚本层面）

已在 [file-formats.md](file-formats.md) §成就注入机制中确认：Steam 版新增了一个独立脚本 `CG_Achievement.ws2`，在展示特定 CG 的指令序列之后，通过一条固定的调用指令触发。已确认 51 处调用点，均插入在原版已有的、显示 CG 的固有指令（含两个内在 id 字段）之后。

尚未确认的是 `CG_Achievement.ws2` 内部具体如何把 CG 编号映射到 Steam 成就 API 调用（该脚本本身只包含一串 id+浮点偏移的数据结构，实际调用 Steam API 的逻辑推测在引擎二进制内，不在脚本层）。若需要在还原内容中新增成就触发点，直接复用 Steam 版脚本里已经写好的调用指令写法即可，不需要理解引擎内部映射逻辑。

## 回想模式（后日谈入口）识别机制 ❓ 待验证

已在 [restoration-targets.md](restoration-targets.md) 中确认原版 `RIO/SL_*.ws2`（`SL_AGE_001`、`SL_AMA_001`、`SL_HUT_001`、`SL_KOT_001`）是四条线各自的后日谈内容，通过回想模式进入，不在主线调用链跳转路径中。已用 `tool/arcbuild.py` 确认这四个脚本**不在** `Rio.arc` 归档内，只以裸文件形式存在于磁盘 `RIO/` 目录（见 restoration-targets.md §6）。尚未确认：

- 引擎如何识别/触发进入回想模式（菜单资源？存档标志位？硬编码判断？）
- Steam 版是否真的整体缺少回想模式入口（初步怀疑缺少，未逐一核实 Steam 版菜单资源与 `Rio.arc`）
- 若还原，除脚本本身外还需还原哪些配套 UI/菜单资源

因涉及菜单系统重建，还原难度高于普通脚本内容删减，**还原优先级较低**，详见 [restoration-targets.md](restoration-targets.md) §6。

## 磁盘裸 `RIO/` 目录是否被引擎读取 ⚠️ 静态分析初步结论，未做运行时验证

原版发行目录下存在一个磁盘裸目录 `RIO/`，除上述 4 个未打包的 `SL_*.ws2` 后日谈脚本外，还有 7 个与 `Rio.arc` 内归档成员**同名但内容有细微差异**的裸文件（`CO1_001/002/003/015.ws2`、`HUT_004/005.ws2`、`start.ws2`，差异明细见 [restoration-targets.md](restoration-targets.md) §7）。这引出一个问题：引擎是否会在运行时读取这个裸目录，与 `Rio.arc` 归档内容混合甚至覆盖？

**已做的排查**：对 `AdvHD.exe`/`AdvHD.dll` 做过 ASCII + UTF-16LE 宽字符串的完整扫描，未发现任何"扫描 RIO/ 目录"“加载裸文件覆盖归档”一类的字符串证据；`AdvHD.exe` 中唯一相关的字符串是归档文件名 `Rio.arc` 本身和通用扩展名 `.ws2`。`AdvPatch.dll` 中的 `a0RiO` 命中经核实是二进制噪声中的偶然字节序列，不是有意义的字符串常量。

**初步结论**：静态字符串证据倾向于支持"引擎只从 `Rio.arc` 归档加载脚本，磁盘裸 `RIO/` 目录不被引擎读取，只是发行包制作过程中的构建残留"。但这只是字符串级排查，没有反汇编归档加载代码路径，也没有做实机 A/B 测试（例如临时清空/改名 `RIO/` 目录看游戏行为是否变化）。**在没有实机验证之前，不应把这个结论当作决定性依据**——如果还原方案的设计依赖"裸目录不会被引擎读取"这一前提，应先补做 A/B 测试。
