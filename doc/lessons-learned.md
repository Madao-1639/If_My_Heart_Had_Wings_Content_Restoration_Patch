# 问题记录

记录调查与开发过程中遇到的具体问题、排查方法和结论。按时间顺序追加，不要事后改写已有条目（除非发现记录本身有误）。

## 1. Windows 控制台打印 Shift-JIS/日文解码结果会报错或乱码

**现象**：用 `print()` 直接输出解码后的日文文本（Shift-JIS 解码为 Python str 后）在 Windows 默认 GBK/cp936 控制台下会抛出 `UnicodeEncodeError` 或显示为乱码字符（如 `全角问号`）。

**原因**：Windows 控制台默认代码页是 GBK（cp936），不是 UTF-8，日文假名/汉字字符不在 GBK 编码范围内。

**解决**：不要直接 print 日文/中文解码结果。改为写入以 `encoding='utf-8'` 打开的文件，再用 Read 工具查看；或者对 stdout 做 `sys.stdout.reconfigure(encoding='utf-8')`（需要确认终端本身也用 UTF-8 显示，否则仍会乱码）。

## 2. arc 归档读取用固定的头部结构即可解析

**方法**：用 8 字节头部（count+table_size）+ 条目表（size、相对偏移、UTF-16LE 文件名）的假设去解析 `Rio.arc`/`Script.arc`，实测头部字段数值与文件末端数据边界完全吻合，成功列出全部成员名与数据。

**结论**：`tool/arcbuild.py` 已实现这套读写逻辑（`verify()`、`read_raw()`），可直接对本游戏全部 `.arc` 文件使用，无需重新实现。写入（打包）功能尚未实测，后续若需要修改归档内容，应先在小归档（如 `Script.arc`，仅 14 个成员）上做写入-回读验证，再用于大归档。

## 3. WS2 脚本编解码方式确认

**方法**：对原版发行版目录下 `RIO/ASA_001.ws2` 尝试逐字节 rotate-left-6 / rotate-right-6 变换，解码结果立即呈现出可读的操作码+Shift-JIS 文本混合结构（`char`、`LAYER_ORDER`、`.PNG` 等 ASCII 关键字清晰可辨）。

**结论**：本游戏的 WS2 编解码方式已确认为逐字节 rotate-6，`tool/ws2.py` 中的 `decode()`/`encode()` 函数可直接使用，无需重新逆向。

## 4. 通过"归档级别的文件名差异"低估了实际删减范围

**现象**：初步对比 Steam 版与原版 `Rio.arc` 的成员名集合，只发现 5 个脚本文件完全缺失（`ASA_002/004`、`YOR_003/005/007`），一度以为这就是全部被删场景。

**纠正**：进一步对比两版本中**同名共存**脚本的解码后长度，发现至少 10 个脚本（`AGE_010`、`AGE_007`、`KOT_009` 等）存在数万字节的长度差异——脚本文件本身仍存在于两个版本中，入口/出口跳转目标相同，但内部对白被原地删除。已验证 `AGE_010.ws2`：删除的是脚本中间一段成人向对白，首尾结构未变。

**教训**：审计 Steam 版内容删减范围时，仅比较"文件是否存在"会严重低估实际范围。必须同时比较同名文件的解码后内容长度（或做逐场景对白比对），才能发现"文件存在但内容被抠空"的情况。这一现象目前只统计了长度差值 >5000 字节的显著案例，实际受影响范围可能更大，需要后续做完整穷尽扫描。

## 5. 同名资源内容不同的真实案例

**现象**：假设"文件名相同就是同一份资源"会导致错误合并/替换。已用 SHA256 对比确认，`CHIP3.arc` 中至少 7 个同名 `.png` 文件（如 `HUT_01_001b.png`）在 Steam 版与原版中字节内容不同，文件大小相差数十 KB。

**教训**：处理任何"同名资源"前，必须先做哈希对比，不能仅凭文件名判断是否需要处理。这类差异很可能是局部裁剪/遮罩编辑（体积略微变小，而非整图替换），具体编辑方式尚未逐像素核实。

## 6. 成就注入点的定位方法

**方法**：不依赖对引擎二进制的静态逆向，而是直接逐字节 diff 同一场景脚本在 Steam 版与原版中的解码内容，寻找 Steam 版比原版多出来的固定字节片段。已确认多出的片段是一条 `\x04 CG_ACHIEVEMENT \x00` 调用指令，插入在原版已有的、显示 CG 的固有指令序列之后。用正则扫描全部 159 个 Steam 脚本验证：全部 920 处 CG 显示指令后都跟着这条调用，覆盖率 100%。

**结论**：这一"逐字节 diff 同一场景两个版本"的方法比静态逆向引擎二进制更快更可靠，是定位 Steam 版新增功能钩子的首选方法。

## 7. Windows GBK 控制台会静默替换非法字符，误导排查方向

**现象**：在排查第 4 条问题时，最初用 `print()` 直接输出提取到的日文文本片段，控制台把大量字符渲染成 `锟斤拷`/问号一类的乱码占位符，一度以为提取逻辑本身出了问题（正则没匹配对）。

**纠正**：改为把提取结果写入 UTF-8 文件再用文件查看工具打开，日文文本正常显示，证明提取逻辑本身没问题，纯粹是控制台编码限制导致的误判。

**教训**：遇到"输出看起来是乱码"的情况，先怀疑显示层（控制台编码）而不是数据层（解码/提取逻辑）——尤其是在已经确认过整体解码流程可行（本项目在第 3 条已验证）之后。

## 8. `oozora_CHSpatch` 汉化译文 CRC32 匹配率 0% → 99.996%：两个独立 bug

**现象**：`tool/extract_script_text.py` 提取的日文原文，按 `oozora_CHSpatch` 的 CRC32 算法计算后在其译文表（`extracted_text.jsonl`）里查找，命中率为 0%。曾一度怀疑是游戏本体存在未记录的二进制补丁改变了 CRC32 输入（详见 `../oozora_CHSpatch/fanchn-crc32-matching-issue.md` §3.4/§3.5），后用 `capstone` 反汇编逐指令追踪证明该补丁只影响目的缓冲区分配大小，不影响传给 `MultiByteToWideChar` 的源字符串内容/长度，这条线索被排除（§3.6）。

**真正原因 1（对话行切分点错误）**：`DIALOGUE_PATTERN` 原来匹配到第一个 `%K` 或 `%P` 就截断（`%[KP]` 非贪婪），但一个对话文本框内可以包含多个由 `%K`（换行等待）分隔的段落，引擎把整段文本（含内嵌 `%K`）当作一次性完整字符串传给 `MultiByteToWideChar` 计算 CRC32。原正则在第一个 `%K` 处截断，取到的只是真实参与计算字符串的前缀，CRC32 必然算错。**修复**：改为匹配到第一个 `%P`（文本框真正结束的标记），允许中间跨越任意个 `%K`。

**真正原因 2（Shift-JIS 解码器选择错误）**：引擎调用 `MultiByteToWideChar(932, ...)`，`932` 是 Windows codepage `cp932`，不是 Python 标准库的 `'shift_jis'` 编解码器。两者对少数字符解码结果不同，典型例子是波浪号：`bytes([0x81,0x60]).decode('shift_jis')` 得到 U+301C（半角波浪号），`.decode('cp932')` 得到 U+FF5E（全角波浪号）——日文口语文本大量使用波浪号表示拉长音，用错编码会导致这些行的字节流与游戏引擎实际处理的不一致，CRC32 随之算错。**修复**：所有 Shift-JIS 编解码统一改为 `cp932`。

**排查方法**：没有靠继续猜候选文本变体，而是先用 `capstone` 反汇编排除"二进制补丁改变输入"这条路径（结构化排除法），再回头系统对比"整行 vs 分段"和"编码器选择"这两个此前只测过一半的维度，逐一在真实 `Rio.arc` 数据上跑百分比统计（不是抽样试几条），才定位到两个叠加的独立 bug——单独修任一个都只能到 76%~99.996% 之间的某个中间值，两个都改才能到 99.996%。

**结论**：两处修复已应用到 `tool/extract_script_text.py`、`tool/extract_dialogue.py`、`tool/generate_lng.py`、`tool/embed_translations.py`。对 `Rio.arc` 全部 160 个脚本重新跑提取+生成 lng 全流程，命中率 50,983/50,985 = 99.996%。剩余 2 条未匹配已逐条核实：1 条是提取正则对紧邻的 `FLAG_CHECK` 分支变量表边界识别错误（把二进制变量数据误当文本拼入，导致解码失败），1 条是译文表本身似乎确实没有对应条目（原因不明）。详见 `../oozora_CHSpatch/fanchn-crc32-matching-issue.md` §3.7/§3.8。

**教训**：遇到"静态分析对不上运行时行为"时，别急着假设"运行时有额外的隐藏逻辑"（虽然这次调查中这个假设一度看起来很有道理，因为确实找到了一处真实存在的二进制补丁）——先用排除法确认输入源头（这里是补丁的下游影响）后，再回头系统检查自己写的提取/编码逻辑本身有没有偷懒的简化（"匹配到第一个标记就停"、"随手选一个看起来对的编解码器名字"），这类问题往往比"游戏引擎有诡异隐藏机制"更常见，也更容易通过读代码+做完整数据集统计发现。
