本文档记录《在这苍穹展翅》（If My Heart Had Wings）的文件格式。以下内容均已通过实际读取本游戏文件验证（Steam 版 `backup/` 与原版发行版目录，见 [restoration-targets.md](restoration-targets.md) 中的路径记录），不是推测。

## Arc 归档容器格式 ✅

### 头部（8 字节）

```
offset 0: count       (uint32, LE)  — 成员数量
offset 4: table_size  (uint32, LE)  — 条目表总字节数
```

无文本 magic 签名。`data_start = 8 + table_size`。

### 条目表（紧随头部，重复 count 次）

```
size            (uint32, LE)  — 成员数据字节数
relative_offset (uint32, LE)  — 相对 data_start 的偏移（不是文件绝对偏移）
filename        (UTF-16LE，以 \x00\x00 结尾)
```

### 已验证的归档内容映射

用 `tool/arcbuild.py` 对 Steam 版与原版发行版的归档做过读取验证，两版数据格式完全一致（同一份代码可无修改读取两版所有归档）。归档文件名与内容类型的对应关系：

| 归档 | 内容 |
|---|---|
| `Rio.arc` | `.ws2` 剧本脚本 |
| `Script.arc` | `.lua` 引擎/UI 逻辑（菜单、画廊、滚动条、语言、版本信息等），**不是**剧本 |
| `GRAPHIC.arc` | CG/背景类图形 |
| `Chip1.arc` / `CHIP2-6.arc` | 角色立绘差分（`.png`，部分场景另附 `.MOS` 同名马赛克变体） |
| `VOICE.arc` | 角色语音（`.ogg`） |
| `SE.arc` | 音效（`.ogg`） |
| `BGM.arc` | 背景音乐（`.ogg`） |
| `SysGraphic.arc` | 系统/菜单图形（`.pna` / `.png`） |
| `SysVoice.arc` | 系统语音（`.ogg`） |
| `Effect.arc` | 特效（`.fx`） |

### 规范化要求 ❓ 未触发过，需留意

尚未在本游戏归档上遇到过表尾 null padding 的情况，但改写归档前应先做校验（读取头部 `table_size` 与条目表实际占用字节数是否吻合），确保改写后重新打包不会因残留 padding 导致哈希不稳定。

## WS2 剧本脚本格式 ✅

### 编解码

逐字节 rotate-left-6 / rotate-right-6（互为逆操作）。已直接解码原版 `RIO/ASA_001.ws2` 与 Steam 版 `Rio.arc` 内的多个脚本，解码结果均为可读的 Shift-JIS 文本与操作码混合内容，未见任何解码失败。

### 已确认的操作码/操作数模式

从实际解码内容中观察到的模式（十六进制，`XX` 代表可变字节）：

- **对话行**：`\x14 <idx:u16> <flag:u16> char\x00 <Shift-JIS文本> %K%P|%P|%K`
  - 格式详解：
    - `\x14`：对话行标记
    - `idx`：2字节小端序无符号整数，lng文件索引
    - `flag`：2字节小端序无符号整数，标志位（用途待确认）
    - `char\x00`：固定标记，表示后续为对话文本
    - 文本内容：Shift-JIS (cp932) 编码
    - 结束标记：`%K%P`（最常见）、单独`%P`、单独`%K`
      - `%K`：换行/等待用户点击
      - `%P`：清空文本框
  - 文本可能包含角色名前缀：`%LC<角色名>\x00`（如 `%LC小鳥\x00`）
  - CRC32计算方法（用于匹配翻译表）：
    1. 提取完整文本（包含 %LC/%K/%P 等标记）
    2. 使用 cp932 解码为 Unicode 字符串
    3. 转换为 UTF-16LE 编码的字节序列
    4. 计算 CRC32，作为有符号 int32（若 ≥ 0x80000000 则减去 0x100000000）
  - 提取正则表达式：`\x14(.{2})(.{2})char\x00((?:[\x80-\xff\x00-\x7f])*?(?:%K%P|%K(?!%P)|(?<!%K)%P))`
- **背景/立绘显示**：`\x33 <槏位名，如 st01/bg01> \x00 <资源名.PNG> \x00 ...` 后紧跟 `LAYER_ORDER` 表
- **跳转/调用到其他脚本**：操作数格式为 `\x02 <脚本名，ASCII 大写，无扩展名> \x00 <4字节数值>`（已在 `ASA_001.ws2` 末尾实测确认，指向 `ASA_002`/`ASA_003` 等）——提取引用时必须用精确字节匹配（脚本名前后有非文本控制字节），不能用朴素子串匹配
- **选择分支菜单**：`\x0f <选项数> [ <id:u16> <选项标签>\x00 <3字节> \x07 <目标脚本名>\x00 ] ...`。标签是**裸 Shift-JIS 文本、无 `%K`/`%P` 标记**；`FLAG_CHECK` 变量表同构（`\x04 FLAG_CHECK \x00 \x0f <项数> [ <id:u16> <标签>\x00 <8字节> ] ...`）。已实测确认（`CO1_013`/`CO1_016_A`/`CO1_018`/`CO2_005`/`HUT_005`），提取见 `tool/scriptext.py` 的 `script_rows()`（`kind='menu'`/`'flag'`）
- **`LAYER_ORDER` 调用与白名单表**：脚本里的 `\x04 LAYER_ORDER\x00` 是 **RunFile 子程序调用**（调用归档内 `LAYER_ORDER.ws2`），不是数据表。`LAYER_ORDER.ws2` 本身是**纯键名白名单**，两版**逐字节相同**（已实测）：
  ```
  0x3f <count:u8=0x13> ev\x00 bg01\x00 bg02\x00 st01\x00…st12\x00 movie\x00 text01\x00 text02\x00 text03\x00 0x05 0xff…
  ```
  → 19 个键（`ev`；`bg01-02`；`st01-12`；`movie`；`text01-03`），**不含位置/坐标**。
- **立绘/背景块指令**（易混）：`\x04 LAYER_ORDER\x00` 之后是若干 `\x09 <index:u16> <float>`（图层权重）与 `\x46 <槽位名>\x00 …`（图层定位）——这是**块的指令流**，不是 `LAYER_ORDER` 表内容。两版该类指令存在增删差异，属演出指令层差异，见 [engine-mechanics.md](engine-mechanics.md)。
- **`0x01` 条件跳转**：**`01 <mode:u8> <id:u16> <val:f32> <a:u32> <b:u32>`**（共 16 字节）。语义统一为「**`var[id] OP val` 成立则顺序执行，否则跳到 `b`**」，`OP` 由 `mode & 0x3F` 决定；`b` 是**解码流内的绝对字节偏移**（真实 Steam 库 2116/2116 个可解析目标全部对齐到指令起点）⇒ 对指令流做任何插入式修改后，`b` 必须按目标指令的新偏移重定基（`script/build/convert_sl_ws2.py` 已实现）：

  ⚠️ **`a` 并非恒 0**：`a` 是第二个候选目标，**`a != 0` 时优先于 `b`**（例：`mainmenu.ws2 @0x38` `var[99] == 100 -> 0x15a (a=0xb8)` 的 if-else-if 派发链）⇒ `a`/`b` 两个字段都要各自重定基，值为 `0` 表示「无此目标」必须跳过。

  ⚠️ **携带绝对偏移的不止 `0x01`**：`0x02` / `0x06`（均 `02|06 <target:u32>`，格式 `04 ff`）是**无条件跳转**，整个操作数即绝对偏移 ⇒ 插入式转换同样必须重定基。`REBASE_OPS = {0x01: (7, 11), 0x02: (0,), 0x06: (0,)}`（值 = 目标 u32 在操作数内的偏移）。

  | `mode & 0x3F` | OP | `mode` 其他位 |
  |---|---|---|
  | 0 | `>=` | bit6(`0x40`)：右操作数也是变量（`val` 作变量下标） |
  | 1 | `<=` | bit7(`0x80`)：走**浮点变量**路径（否则走布尔变量位图路径） |
  | 2 | **`==`** | |
  | 3 | **`!=`** | |
  | 4 | `>` | |
  | 5 | `<` | |

  `2`/`3` 的取向由 `sub_459DA0` 的反汇编（jumptable case 2/3 的 `ucomiss` + `lahf`/`test ah,44h`/`jnp` 走向）判明，并用 `CG_Achievement.ws2`、`mainmenu.ws2`（`var99 == 105`、`var127 == 0`）三处独立用法交叉验证。
- **`0xF0` 成就触发**：`f0 <idx:u8>`（共 2 字节）。`idx` = Steam 成就枚举序的 0 基序号；越界（本作成就数 = 20）则为空操作。引擎分发表表项 240 → `sub_46AC00` = `ISteamUserStats::SetAchievement` + `StoreStats`。触发契约见 [engine-mechanics.md](engine-mechanics.md) §成就触发点契约；完整映射见 [achievement-mechanics.md](achievement-mechanics.md)。
- **`0x09` 变量设置**：`09 <mode:u8> <id:u16> <val:f32>`（共 8 字节）。`mode=0` 赋值、`mode=1` 累加（`var[id] += val`）。
- **`0x0b` 布尔变量设置**：`0b <id:u16> <val:u8>`（共 4 字节）。
- **格内指令的归属次序 ✅**：一个文本单元的典型排布是 **演出指令（`0x33`/`0x34`/`0x1e` 及其 `LAYER_ORDER` 块）→ `0x28` 语音 → `0x15` 名字框 → `0x14` 文本**。⇒ 语音与画面 token 归**其后最近的一条 `0x14`**；该行自身不带时**沿用前一格**的生效值（语音与画面都是延续语义）。承载图取数、`script/verify_sync.py` 的逐槽对账、`tool/scriptext.script_rows()` 的 dlg/ctrl 序都用这一口径。
  - 连带后果：删格（`tool/writer.drop_units()`）只摘被删行的 `0x14` 与其邻接 `0x15` ⇒ 该行**前面的演出与语音指令整段留在原地**，按上述口径落进**后继格**的归属区（表现为"无对白连播语音""画面/立绘/BGM 回退"）。分诊与处置见 [restoration-route.md](restoration-route.md) §7 V-9、[lessons-learned.md](lessons-learned.md) §26。

### 两版操作数格式表与原版脚本转换

引擎在二进制内自带一张 **256 项操作数格式表**（指针数组，每项指向 `0xff` 终止的操作数类型码串；类型码 `0/1`=u8(u16)、`2`=u16、`5`=f32、`6/9/10`=str、`8`=0B、`7`=变长块）。这是 WS2 线性解析的**权威依据**：

- **Steam 表**：脱壳 exe `off_553EC0`，即 `tool/ws2fmt.txt`（158 项非空）。
- **原版表**：原版 `AdvHD.exe`（未加壳）`.data` 内文件偏移 **`0x1212c0`**（98 项非空；自校验：entry[0x21] 必须指向 `06 08 01 01 01 ff`）。

两表逐项差分：

1. **Steam = 原版 + 尾部操作数 + 新增操作码**，不存在「原版有、Steam 无」的操作码（第三类差分为空）⇒ 原版脚本转换到 Steam 编码总是可行。
2. 格式不同的操作码共 9 个，新增操作数的取值**恒定**（依据见下表后的「插入取值的独立验证」）。⚠️ **`CO1_001`/`CO1_002`/`CO1_003`/`CO1_015`/`HUT_004` 等同名配对脚本不能用于验证取值**：这几组成员的指令序列在 Steam 侧本就不同（`CO1_001` 原版首条 `0x16` vs Steam `0xf0`；`CO1_003`/`CO1_015`/`HUT_004` 在指令 4–5 处 Steam 已删/改演出指令），naive 序号对齐会把不同指令的操作数配在一起。同名配对只用于确认「操作码存在性与格式表差分」。

| op | 原版 fmt | Steam fmt | 转换（实测取值） |
|---|---|---|---|
| `0x11` | `06 08 05` | `06 08 00 05` | str 与 f32 间插 `0x00` |
| `0x14` | `04 06 08 06 08` | `… 00` | 尾插 `0x00`（全库 43886 条验证） |
| `0x15` | `06 08` | `… 00` | 尾插 `0x00`（87739 条） |
| `0x16` | `00` | `00 00` | 尾插 `0x00`（7950 条） |
| `0x1c` | `06 08 06 08 01` | `… 00` | 尾插 `0x00`（SL 脚本不含，未用） |
| `0x1e` | `… 00` | `… 00 05` | 尾插 f32 `0.0`（1149 条） |
| `0x28` | `… 00` | `… 00 05` | 尾插 f32 `0.0`（20947 条） |
| `0x35` | `06 08 0a 08 00 00` | `… 00` | 尾插 `0x01`（SL 脚本不含，未用） |
| `0x56` | （中段插 4×f32 + 尾插 f32） | | SL 脚本不含，未用 |

   **插入取值的独立验证（不依赖配对脚本）**：直接统计 Steam 自身 159 个成员里「被插入字段」的实际取值 —— `0x11` 的 `ops[-5]`（u8）1552/1552 全为 `0`；`0x14` 的 `ops[-1]` 43881/43886；`0x15` 87739/87739；`0x16` 7950/7950；`0x1e` 的尾 f32 1149/1150 为 `0.0`；`0x28` 20947/20948。**全部「非零反例」都出自同一个成员 `CG_PAGE09.ws2`**，而该成员按 Steam 表**线性解析本身就会失步**（反读到的字节落在字符串中部，如 `...4855`=`HU`、`...6e0100001c`），故不构成真反例。⇒ 插入值由 Steam 原生数据证实，而非假设。
   ⚠️ 已知解析器鲁棒性缺口：`CG_PAGE09.ws2`（以及原版 `CG_PAGE09` 报 `unexpected tableless op 0xe2`）不能用线性解析处理，`ws2dis.disassemble()` 的 `ok` 标志只校验尾部长度、**不能识别中途失步**。本体（L1–L3）若要复用转换器，必须先补 `0x1c`/`0x35`/`0x56` 的格式差（`CONV` 目前只覆盖 SL 用到的 6 个），并单独处理该成员。
   ⚠️ **`0x1b` 是唯一的「原版格式更大」特例（`CO1_016_A` 触发）**：原版描述符抽取只出 `[0]`，实际形状为 `[0,6,8,6,8,10,8]`（前导 u8 + 内嵌字符串组；尾段写法 `1b 00 "好きです" …`，steam 侧同内容拆成 `1b 00`＋`49 " like it"` 两个操作码）。`load_orig_formats()` 已显式补该表项（判据 = 全库 158 个 orig 脚本线性解析自洽、其余脚本 0x14 计数不变、字符串正确解出「好きです」）。**它同时违反上表「Steam = 原版 + 尾部操作数」的单向性**：orig→steam 转换只会补字节不会删字段 ⇒ **含 `0x1b` 的 orig span 不得进插入区间**（`CO1_016_A` 的 `0x1b` 在末行 span，正常还原不触及；全库仅 `CO1_016_A` 与 `MAINMENU` 含 `0x1b`）。

3. **格式一致的操作码，操作数字节两版逐字节相同**（数万对齐对零差异）⇒ 转换时原样复制。
4. **跳转目标重定基**：`0x01` 的 `b`、`0x02`/`0x06` 的目标都是解码流内绝对字节偏移 ⇒ 插入式转换后必须按目标指令的新偏移重写（`convert_sl_ws2.py` 两遍转换实现，回读断言目标落在指令起点）。**4 个 `SL_*` 全量携带者清单（实测，逐条）**：

   | 位置 | 指令 | 原目标 | 门控 | 执行路径 |

   | 尾部 | `01.b -> 续场段` ×2 | **需重定基** | `flag[127]==1` / `var[110]==N`（**不成立才跳**） | **正常路径必然执行**（即 H 场景→下一场景的退出口） |

   `flag127`（回想模式标记）全库**只由 `mainmenu.ws2 @0x308` 置 1**，位于 `var99 == 2`（回想按钮）分支；`var110`（回想条目序号 1–21）**只由 `REPLAY_EXE.ws2` 写**。海报入口（`var99 == 105` → `openAfter` → `flag126 = 1` → `NextFile SL_*`）不触碰 127 ⇒ 头部 `06` 在正常路径不可能执行。⚠️ 且 **Steam 版整条回想入口结构性缺失**（`menu_gallery.lua` 条目表只到 `REPLAY_017`、`SceneMenu.PageMax = 2` ⇒ `var101 == 3` 与「第 2 页第 9 条」都取不到，见 [afterstory-mechanics.md](afterstory-mechanics.md) §5.3），所以头部那条 `06` 在 Steam 侧为不可达代码。

### 成就注入机制 ✅ 已完全确认（脚本层 + 引擎层）

Steam 版 `Rio.arc` 中存在一个原版没有的独立脚本 `CG_Achievement.ws2`（9606 字节），是一段**以 CG 编号为键、维护 CG 收集计数并触发收集类成就的 VM 字节码**。触发契约见 [engine-mechanics.md](engine-mechanics.md) §成就触发点契约；完整映射链（29 处 `0xF0` 触发点 → 20 项成就）见 [achievement-mechanics.md](achievement-mechanics.md)。

**结构 ✅ 已逐字节复核**（解码后 9606 字节 = 8 字节头 + 395 × 24 字节记录 + 118 字节尾部）：

```
头        : 09 00 37 00 00 00 00 00                  ; LayerConfig(mode=0, id=55, 0.0) —— 初始化 CG 计数器
每条记录  : 01 02 <u16 CG编号> 00 00 80 3f           ; Condition(mode=2, id=CG编号, val=1.0, b=下一记录)
            00 00 00 00 <u32 下一记录偏移>           ; a = 0；b 恒为 (本记录偏移 + 24)，正向链表
            09 01 37 00 00 00 80 3f                  ; LayerConfig(mode=1, id=55, 1.0) —— var[55] += 1.0
尾部      : 6 × [ Condition(mode=0x80, id=55, <float 阈值>, b=下一块) + F0 <u8 idx> ] + 05 + ff + 8 字节尾
```

- **本文件是 VM 字节码，不是不透明数据表**。每条记录语义：`if (var[CG编号] == 1.0) var[55] += 1.0`（`0x01` 的 `mode&0x3F == 2` 即 `==`：成立则顺序执行，否则跳 `b`）。`var[CG编号]` 由显示点处的 `0x0b <CG编号> 01` 置 1。
- 395 条记录的 CG 编号 = **1190 … 2674**，严格递增、互不重复；表内**无任何 ASCII 字符串**（成就名不在脚本层）。
- 尾部 6 条 `F0 <u8>` 是**成就触发指令**（`F0` = `SetAchievement`，完整映射见 [achievement-mechanics.md](achievement-mechanics.md)），阈值依次为 **1 / 79 / 158 / 237 / 316 / 395**（即 1 个 CG 与 **20% / 40% / 60% / 80% / 100% × 395**），索引 `14/15/16/17/18/19` ⇒ 成就 `IMH_ACHIEVEMENT_15..20`（First Contact / Approach / Take-Off / Soar / Glide / Morning Glory）。
- 常量尾巴 `09 01 37 00 00 00 80 3f` 在 `Rio.arc` 全部 **158 个 `.ws2`** 中**只出现在本文件**（395 次），是成就表专用模板；记录里的 `01 02 <u16> 00 00 80 3f` 则是通用写法（其他脚本共 1420 次，见 `CG_PAGE01-12`、`FLAG_CHECK` 等）。

**键值对应 ✅ 已核对**：`CG_Achievement.ws2` 的 395 个编号集合 **= 全部 CG 显示点的第二个 `0x0b` 变量（B）取值集合（394 个）∪ {1195}**，一一对应、无一遗漏；表内多出的 `1195` 在 Steam 脚本中没有任何显示点（疑似被删 CG 的遗留条目）。

对比同一场景脚本（如 `AGE_001.ws2`）在 Steam 版与原版的对应位置，发现显示 CG 的指令序列中，Steam 版比原版多出一段：

```
原版：  ...LAYER_ORDER\x00 <resource-id>04 01 0b <id2> \x01\x04 LAYER_ORDER\x00...
Steam版：...LAYER_ORDER\x00 <resource-id>04 01 0b <id2> \x01\x04 CG_ACHIEVEMENT\x00 \x04 LAYER_ORDER\x00...
```

即：显示 CG 的固有指令（含两个内在 id 字段，原版就存在，与成就无关）之后，Steam 版额外插入了一条 `\x04 CG_ACHIEVEMENT \x00` 调用指令。已确认 51 个脚本文件包含对 `CG_ACHIEVEMENT` 的调用；用正则匹配全部 0x33 CG 显示指令逐一核对，Steam 版 `Rio.arc` 全部 **158 个 `.ws2`** 中共有 920 处 CG 显示，全部 920 处紧跟成就调用，覆盖率 100%——即 Steam 版对每一次 CG 显示都无条件注入了这条调用，不是选择性注入。

**注入方法（已实现并验证，见 `tool/ws2.py` 的 `inject()`）**：向脚本中插入内容时，若该场景在 Steam 版中存在对应的 CG 显示点，直接复用 Steam 版脚本中已经写好的这条调用指令，绝不重新计算或编造内在的 id 字段。已验证：从一段真实 Steam 脚本中剥离全部成就调用后，用 `inject()` 重新处理，可以逐字节还原出原始 Steam 版脚本。

**调用点的两个 id 字段 ✅ 已定性**（920 处全量统计）：

| 字段 | 取值域 | 去重 | 含义 |
|---|---|---|---|
| 第一个 `0x0b` 的 u16（A） | 1089 … 1189 | 69 个 | CG 所属的**场景/图库分组** |
| 第二个 `0x0b` 的 u16（B） | 1190 … 2674 | 394 个 | **该 CG 的编号 = 索引 `CG_Achievement.ws2` 的键** |

⇒ 引擎侧的映射是「**CG 编号（B）→ `CG_Achievement.ws2` 条目 → CG 计数 `var[55]` → 收集里程碑 `F0 idx`**」；成就数据与触发条件完全由脚本层决定，**引擎只负责按 `F0` 的 idx 查运行时表并调用 Steam API**（表由 Steam 的 `GetAchievementName(i)` 顺序构建，见 [engine-mechanics.md](engine-mechanics.md)）。故**只要复用 Steam 版脚本里原样写好的 `0x0b` 变量对 + 那条 16 字节调用，就必然复现原版成就行为**，无需理解引擎内部实现。

## 已确认的图形资源删减/差异范围

已直接对比多个 CHIP 归档，确认两类差异：

1. **原版独有的立绘差分整档缺失**：例如 `CHIP2.arc`（AGE 角色）原版比 Steam 版多 305 个 `.png` 文件，`CHIP3.arc`（HUT 角色）原版多 366 个，`CHIP6.arc`（AMA 角色）原版多 239 个。命名模式为 `<角色代码>_<场景编号>_<差分编号><B/S><.png>`（`B`/`S` 后缀已确认为 Big/Small 两种分辨率变体，非内容差异，详见 [pna-resources.md](pna-resources.md)）
2. **同名文件内容不同**（真实存在的"同名冲突"）：已用 SHA256 逐一验证，例如 `CHIP3.arc` 中的 `HUT_01_001b.png`、`HUT_01_002s.png` 等文件，Steam 版与原版同名但字节内容不同。**已逐像素核实差异形态**：这类改动是 Steam 对原版画面的**和谐改画**，有两种形态——**叠加遮挡重画**（如给人物补上织物）与**取景变化**（放大后裁掉裸露区域）；也存在两侧同尺寸而内容不同的情形 ⇒ 尺寸差与体积差都不能当分类判据，**「全库最近邻命中别的帧」也不能定号位复用**（取景变化的必然结果）。处置：**噪声不动，其余同名内容差一律整名覆盖回原版**（顶包也不隔离改名，只在**还原后仍保留的 Steam 格**上改写那一个显示调用点）；判据五步见 [resource-naming.md](resource-naming.md) §2。这确认了"Steam 版复用原版文件名但内容被重新编辑"这类冲突在本游戏中确实存在，替换资源时不能假设同名文件内容相同

## `.MOS` 马赛克变体 ✅ 身份已确认，选用机制待查

原版部分角色立绘目录（如 `CHIP3.arc` 的 HUT_10、CHIP6.arc 的 AMA_10）中，同名 `.png` 文件旁存在一个同名的 `.MOS` 文件（如 `HUT_10_006S.MOS` 与 `HUT_10_006S.png` 并存）。**已确认 `.MOS` 是马赛克遮罩变体**（本身也是合法 PNG，相同的 PNG magic bytes，但文件明显更小——12995 字节 vs 对应 png 的 1009838 字节）。

选用机制仍待查：已对原版 `Rio.arc` 全部 161 个脚本做过完整扫描（非抽样），确认没有任何脚本引用过 `.MOS` 扩展名。进一步核实：脚本中引用了与 `.MOS` 同名的图片 stem（如 `AMA_10_005B`）时，一律写作 `<stem>.PNG`，从未写作 `<stem>.MOS`（例如 `AMA_004.ws2` 中出现的是 `AMA_10_005B.PNG`）。说明脚本本身永远只请求 `.PNG`，`.MOS` 与 `.PNG` 之间的切换是引擎在加载资源时自行决定的，不受脚本控制。具体触发条件（游戏内审查开关？系统区域检测？）尚未查明，见下方待办。
