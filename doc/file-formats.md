# 文件格式规范

本文档记录《在这苍穹展翅》（If My Heart Had Wings）的文件格式。以下内容均已通过实际读取本游戏文件验证（Steam 版 `backup/` 与原版发行版目录，见 [restoration-targets.md](restoration-targets.md) 中的路径记录），不是推测。

- ✅ **已确认**：已直接读取/解码本游戏文件验证
- ⚠️ **部分确认**：结构已验证，细节（如全部操作码语义）尚未穷尽
- ❓ **未知**：尚待调查

## Arc 归档容器格式 ✅

### 头部（8 字节）

```
offset 0: count       (uint32, LE)  — 成员数量
offset 4: table_size  (uint32, LE)  — 条目表总字节数
```

无文本 magic 签名。`data_start = 8 + table_size`。

### 条目表（紧随头部，重复 count 次）

```
size            (uint32, LE)  — 成员数据字节数
relative_offset (uint32, LE)  — 相对 data_start 的偏移（不是文件绝对偏移）
filename        (UTF-16LE，以 \x00\x00 结尾)
```

### 已验证的归档内容映射

用 `tool/arcbuild.py` 对 Steam 版与原版发行版的归档做过读取验证，两版数据格式完全一致（同一份代码可无修改读取两版所有归档）。归档文件名与内容类型的对应关系：

| 归档 | 内容 |
|---|---|
| `Rio.arc` | `.ws2` 剧本脚本 |
| `Script.arc` | `.lua` 引擎/UI 逻辑（菜单、画廊、滚动条、语言、版本信息等），**不是**剧本 |
| `GRAPHIC.arc` | CG/背景类图形 |
| `Chip1.arc` / `CHIP2-6.arc` | 角色立绘差分（`.png`，部分场景另附 `.MOS` 同名马赛克变体） |
| `VOICE.arc` | 角色语音（`.ogg`） |
| `SE.arc` | 音效（`.ogg`） |
| `BGM.arc` | 背景音乐（`.ogg`） |
| `SysGraphic.arc` | 系统/菜单图形（`.pna` / `.png`） |
| `SysVoice.arc` | 系统语音（`.ogg`） |
| `Effect.arc` | 特效（`.fx`） |

### 规范化要求 ❓ 未触发过，需留意

尚未在本游戏归档上遇到过表尾 null padding 的情况，但改写归档前应先做校验（读取头部 `table_size` 与条目表实际占用字节数是否吻合），确保改写后重新打包不会因残留 padding 导致哈希不稳定。

## WS2 剧本脚本格式 ✅

### 编解码

逐字节 rotate-left-6 / rotate-right-6（互为逆操作）。已直接解码原版 `RIO/ASA_001.ws2` 与 Steam 版 `Rio.arc` 内的多个脚本，解码结果均为可读的 Shift-JIS 文本与操作码混合内容，未见任何解码失败。

### 已确认的操作码/操作数模式

从实际解码内容中观察到的模式（十六进制，`XX` 代表可变字节）：

- **对话行**：`\x14 <idx:u16> <flag:u16> char\x00 <Shift-JIS文本> %K%P|%P|%K`
  - 格式详解：
    - `\x14`：对话行标记
    - `idx`：2字节小端序无符号整数，lng文件索引
    - `flag`：2字节小端序无符号整数，标志位（用途待确认）
    - `char\x00`：固定标记，表示后续为对话文本
    - 文本内容：Shift-JIS (cp932) 编码
    - 结束标记：`%K%P`（最常见）、单独`%P`、单独`%K`
      - `%K`：换行/等待用户点击
      - `%P`：清空文本框
  - 文本可能包含角色名前缀：`%LC<角色名>\x00`（如 `%LC小鳥\x00`）
  - CRC32计算方法（用于匹配翻译表）：
    1. 提取完整文本（包含 %LC/%K/%P 等标记）
    2. 使用 cp932 解码为 Unicode 字符串
    3. 转换为 UTF-16LE 编码的字节序列
    4. 计算 CRC32，作为有符号 int32（若 ≥ 0x80000000 则减去 0x100000000）
  - 提取正则表达式：`\x14(.{2})(.{2})char\x00((?:[\x80-\xff\x00-\x7f])*?(?:%K%P|%K(?!%P)|(?<!%K)%P))`
- **背景/立绘显示**：`\x33 <槏位名，如 st01/bg01> \x00 <资源名.PNG> \x00 ...` 后紧跟 `LAYER_ORDER` 表
- **跳转/调用到其他脚本**：操作数格式为 `\x02 <脚本名，ASCII 大写，无扩展名> \x00 <4字节数值>`（已在 `ASA_001.ws2` 末尾实测确认，指向 `ASA_002`/`ASA_003` 等）——提取引用时必须用精确字节匹配（脚本名前后有非文本控制字节），不能用朴素子串匹配
- **LAYER_ORDER 表**：格式为 `\x04 LAYER_ORDER \x00 F<槏位名>\x00` 后跟固定长度的位置量数组，紧接一组 `\x09 <index:u16> <float>` 形式的图层权重设置

### 成就注入机制 ✅ 已定位，机制已确认

Steam 版 `Rio.arc` 中存在一个原版没有的独立脚本 `CG_Achievement.ws2`（9606 字节，解码后是一连串 `\x09 ... \x01\x02 <id> \x04 ...` 结构，逐条记录 CG 编号与百分位偏移，用于成就进度统计）。

对比同一场景脚本（如 `AGE_001.ws2`）在 Steam 版与原版的对应位置，发现显示 CG 的指令序列中，Steam 版比原版多出一段：

```
原版：  ...LAYER_ORDER\x00 <resource-id>04 01 0b <id2> \x01\x04 LAYER_ORDER\x00...
Steam版：...LAYER_ORDER\x00 <resource-id>04 01 0b <id2> \x01\x04 CG_ACHIEVEMENT\x00 \x04 LAYER_ORDER\x00...
```

即：显示 CG 的固有指令（含两个内在 id 字段，原版就存在，与成就无关）之后，Steam 版额外插入了一条 `\x04 CG_ACHIEVEMENT \x00` 调用指令。已确认 51 个脚本文件包含对 `CG_ACHIEVEMENT` 的调用；用正则匹配全部 0x33 CG 显示指令逐一核对，Steam 版全部 159 个脚本中共有 920 处 CG 显示，全部 920 处紧跟成就调用，覆盖率 100%——即 Steam 版对每一次 CG 显示都无条件注入了这条调用，不是选择性注入。

**注入方法（已实现并验证，见 `tool/ws2.py` 的 `inject()`）**：向脚本中插入内容时，若该场景在 Steam 版中存在对应的 CG 显示点，直接复用 Steam 版脚本中已经写好的这条调用指令，绝不重新计算或编造内在的 id 字段。已验证：从一段真实 Steam 脚本中剥离全部成就调用后，用 `inject()` 重新处理，可以逐字节还原出原始 Steam 版脚本。

## 已确认的 Steam 版删减范围（脚本层面）

已直接对比 Steam 版与原版的 `Rio.arc`，确认：

- 原版存在 `ASA_002.ws2`、`ASA_004.ws2`、`YOR_003.ws2`、`YOR_005.ws2`、`YOR_007.ws2` 五个脚本，Steam 版完全没有这些文件
- Steam 版的 `ASA_001.ws2` 结尾直接跳转到 `ASA_003`（跳过 `ASA_002`），原版的 `ASA_001.ws2` 结尾跳转到 `ASA_002`；Steam 版 `ASA_003.ws2` 结尾跳转到 `ASA_005`（跳过 `ASA_004`），原版跳转到 `ASA_004`——即 Steam 版通过**直接改写跳转目标**把中间的场景整段跳过，而不是保留一个阉割版脚本占位
- 脚本解码后长度不能直接用来判断内容增减：例如 `ASA_001.ws2` 原版解码长度 160025 字节，Steam 版反而更长（172464 字节），这是因为 Steam 版脚本中插入了大量成就调用指令（每处 CG 显示后 16 字节），抵消甚至反超了被删对白造成的长度损失。必须扣除成就调用指令的字节数之后再比较，或者直接比对具体文本内容差异，不能只看解码后总长度的正负号判断是否存在删减
- `Script.arc` 中，Steam 版比原版多出 11 个 `.lua` 文件（`menu_gallery.lua`、`menu_config.lua`、`ui_button.lua` 等），原版这些 UI 逻辑可能内嵌在别处或版本更旧不含这些功能——原版是较早的引擎构建版本，Steam 版做了 UI 系统升级，这部分差异与内容删减无关，不应误判为"被删内容"

## 已确认的图形资源删减/差异范围

已直接对比多个 CHIP 归档，确认两类差异：

1. **原版独有的立绘差分整档缺失**：例如 `CHIP2.arc`（AGE 角色）原版比 Steam 版多 305 个 `.png` 文件，`CHIP3.arc`（HUT 角色）原版多 366 个，`CHIP6.arc`（AMA 角色）原版多 239 个。命名模式为 `<角色代码>_<场景编号>_<差分编号><B/S><.png>`（`B`/`S` 后缀已确认为 Big/Small 两种分辨率变体，非内容差异，详见 [pna-resources.md](pna-resources.md)）
2. **同名文件内容不同**（真实存在的"同名冲突"）：已用 SHA256 逐一验证，例如 `CHIP3.arc` 中的 `HUT_01_001b.png`、`HUT_01_002s.png` 等 7 个文件，Steam 版与原版同名但字节内容不同、文件大小有差异（约几十 KB 差异，怀疑是裁剪/局部遮罩）。这确认了"Steam 版复用原版文件名但内容被重新编辑"这类冲突在本游戏中确实存在，替换资源时不能假设同名文件内容相同

## `.MOS` 马赛克变体 ✅ 身份已确认，选用机制待查

原版部分角色立绘目录（如 `CHIP3.arc` 的 HUT_10、CHIP6.arc 的 AMA_10）中，同名 `.png` 文件旁存在一个同名的 `.MOS` 文件（如 `HUT_10_006S.MOS` 与 `HUT_10_006S.png` 并存）。**已确认 `.MOS` 是马赛克遮罩变体**（本身也是合法 PNG，相同的 PNG magic bytes，但文件明显更小——12995 字节 vs 对应 png 的 1009838 字节）。

选用机制仍待查：已对原版 `Rio.arc` 全部 161 个脚本做过完整扫描（非抽样），确认没有任何脚本引用过 `.MOS` 扩展名。进一步核实：脚本中引用了与 `.MOS` 同名的图片 stem（如 `AMA_10_005B`）时，一律写作 `<stem>.PNG`，从未写作 `<stem>.MOS`（例如 `AMA_004.ws2` 中出现的是 `AMA_10_005B.PNG`）。说明脚本本身永远只请求 `.PNG`，`.MOS` 与 `.PNG` 之间的切换是引擎在加载资源时自行决定的，不受脚本控制。具体触发条件（游戏内审查开关？系统区域检测？）尚未查明，见下方待办。

另外已确认：Steam 版 `CHIP3.arc`、`CHIP6.arc` 中 `.MOS` 文件已被**整批移除**（数量为 0），Steam 版脚本中也不存在任何 `.MOS` 引用。也就是说 `.MOS` 变体属于 Steam 版删减范围的一部分，还原内容时如果涉及到原版中曾经存在 `.MOS`/`.png` 并存的立绘，需要考虑是否要一并带回 `.MOS` 变体（取决于是否需要还原引擎的马赛克切换行为，还是只需要保留清晰版 `.png` 即可）。

## 字符编码规则 ✅

- 归档成员名：UTF-16LE（已确认）
- 脚本内容中的对白/资源名：Shift-JIS（已确认，解码样本可正常按 Shift-JIS 显示日文）
- 中文译文：不出现在原始脚本中；若要参考现成中文翻译，应去独立的中文化补丁资源中找，不要尝试在原始脚本里搜索中文关键词
- Windows 控制台默认 GBK/cp936 编码，非 ASCII 的 print 输出可能崩溃，需要用 ASCII 标记或强制 UTF-8 reconfigure
