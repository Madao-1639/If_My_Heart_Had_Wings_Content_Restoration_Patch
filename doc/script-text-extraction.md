# 脚本文本提取与匹配验证

## 1. 提取方法

### 1.1 文本来源

**Rio.arc**（50,990 条文本）：
- 主要游戏脚本存储在 `Rio.arc` 中
- 包含所有常规剧情对话

**RIO目录**（7,277 条文本）：
- 位于 `游戏目录/RIO/` 下的独立脚本文件
- 包含特殊场景（H场景等）和补充内容
- 文件列表：CO1_001.ws2, CO1_002.ws2, CO1_003.ws2, CO1_015.ws2, HUT_004.ws2, HUT_005.ws2, SL_AGE_001.ws2, SL_AMA_001.ws2, SL_HUT_001.ws2, SL_KOT_001.ws2, start.ws2

**总计**：58,267 条文本，49,922 个唯一CRC32

### 1.2 对话行格式

```
\x14 <idx:u16> <flag:u16=0> <speaker\0> <Shift-JIS 对白>(%K%P|%K|%P) \0
```

- `idx` = 槽位号（= `lng_idx`）；`speaker` 实测只有 `char`（对白）与空（清屏行，文本恰为 `%P`）两种。
- 解析用**结构化行解析**（见 §6.2），**不要**用正则硬编码 `char\0`——会漏掉 18 条空说话人清屏行。

**CRC32（引擎查表键）**：文本（含 `%K`/`%P` 标记）→ cp932 解码 → UTF-16LE 编码 → CRC32（有符号 int32）。

### 1.3 选择分支菜单选项格式

选项标签是**裸日文（无 `%K`/`%P` 标记）**，位于 `\x0f <选项数>` 引导的块内：

```
\x0f <选项数> [ <id:u16> <标签>\x00 <3字节> \x07 <目标脚本名>\x00 ] ...
```

- 标签紧跟 `\x00` 后是 3 字节参数，再是 `\x07` + 分支目标脚本名 + `\x00`
- `FLAG_CHECK` 变量表同构：`\x04 FLAG_CHECK\x00 \x0f <项数> [ <id:u16> <标签>\x00 <8字节> ] ...`
- 提取见 `tool/scriptext.py` 的 `script_rows()`（`kind='menu'`，用 `\x07<NAME>\x00` 作锚点，向前跨 3 字节定位标签）

## 2. 匹配验证结果

### 2.1 双向验证方法

**正向验证**（提取的原版日文文本 → 民汉表）：
- 检查我们提取的每条文本是否在民汉表中有对应译文
- 评估提取质量：确保我们提取的是有效的游戏文本

**反向验证**（民汉表 → 提取的原版日文文本）：
- 检查民汉表中的每条译文是否能在我们提取的文本中找到对应日文
- 评估覆盖率：确保民汉译文能被充分利用

### 2.2 验证结果

注意：**反向验证必须把"独立的角色名标记（`%LC<角色名>`）"和"选择分支菜单选项标签"也计入提取集合**，否则会被误判为未覆盖。提取集合 = 对话行 49,920 + 角色名标记 99 + 菜单选项 14 = **50,033** 个唯一 CRC32。计入后：

| 验证方向 | 结果 | 说明 |
|---------|------|------|
| 正向（提取 → 民汉） | 99.996% (50,031/50,033) | 提取的文本几乎全部有译文；未匹配 2 条 |
| 反向（民汉 → 提取） | 99.982% (50,031/50,040) | 民汉表的译文覆盖率；未匹配 9 条 |
| 反向未匹配 | 9 条 | 7 条冗余异形 + 2 条待查（见 3.2） |

**结论**：99.98% 以上的双向覆盖率证明提取方法正确且完整。剩余未匹配均已定性归属（见第 3 节）。

**9 条"同句异形/子串"的成因**：

- **`%K` / `%K%P` 异形（7 条）**：脚本行 `先輩が、ちょっと残念そうにつぶやく。%K`（crc=783337970，已匹配），表中另存 `…つぶやく。%K%P`（crc=-2045702704）；`%LC%XS35飞　　　鱼　　　庄` 的两种空格写法同理。
- **尾部子串（同属上类）**：脚本行 `足りなくなった部員数はどうしようか。%K%P`（crc=804167420，已匹配），表中另存其尾部片段 `どうしようか。%K%P`（crc=-1222977892）。
- **待查（2 条）**：`「还好是这个半路陈咬金」%K%P`、`大概在哪里，已经检讨完毕了。%K%P`，表中无同文异形条目。

**控制符以脚本内日文原文为准**：脚本日文已写明 `%K`（换行等待）或 `%K%P`（换行+清屏），即引擎实际使用的形式；表中"同句异形"条目是冗余，反向未匹配≠缺译文。对话行按 `lng_idx` 映射时只看主行，主行 100% 有译文。

**验证方法补充**：CRC32 反推（对候选日文直接计算 CRC32 比对目标值）可确认表中条目对应的真实日文——如 `怎么办好呢。%K%P` 反推为 `どうしようか。%K%P`。

## 5. 行模型 `tool/scriptext.py`

一个脚本的"文本行"= 脚本内所有会被显示层消费的字符串，按字节偏移排序，四类：

| `kind` | 形态 | 槽位 |
| --- | --- | --- |
| `dlg` | `\x14 <idx:u16> <flag=0> <speaker\0> <text>%K%P|%%K|%P\x00` | `idx` |
| `ctrl` | 同上但 speaker 为空（清屏行，text 恰为 `%P`） | `idx` |
| `name` | `\x15 %LC<名>\x00` | 无（独立原始行，不占 idx） |
| `menu` | `\x0f` 选项块内 `<id:u16> <标签>\x00 … \x07<目标脚本>\x00` | `id` |
| `flag` | `FLAG_CHECK` 变量表内 `<id:u16> <标签>\x00` | `id` |

接口：`script_rows(name, data)` 出单脚本行（含噪声排除与重复 idx 断言）、`collect_scripts(orig_dir)` 按铺表序取 `[(脚本名, ws2 字节, 来源)]`、`all_rows(orig_dir)` 全库拼接、`crc32_signed(bytes)` 出引擎口径查表键。原版素材目录由环境变量 `IFMH_ORIG_DIR` 提供。

消费方：`script/align_corpus.py`（语料行对齐）、`script/build_fan_translations.py`（出包）、`script/build_carrier_map.py`、`script/build_l4.py`、`script/convert_sl_ws2.py`、`tool/v5lib.py`。

**噪声排除**：`\x14` 巧合命中二进制块（flag≠0、speaker 不是 char/空、text 含 NUL、空 speaker 但 text 不是 `%P`）一律丢弃；`FLAG_CHECK` 扫描只认真标签——真标签必 cp932 可解码且含非 ASCII 字符，纯 ASCII 的是二进制巧合命中，否则 `CO1_018` 这类脚本的槽位数会虚增到 3 万余。

## 6. 民汉中文文本产物生成（`script/build_fan_translations.py`）✅ 已验证

把民汉表译文按本节规则组织为 `resource/fan_cn/` 下的**逐脚本 JSON**（`{SCRIPT}.json`，`idx → 中文文本`，只写有行的槽位）。**主产物不是 lng**：原版脚本不消费 lng，Steam 版也不能直接装载它（要先按官方脚本的改动改造），所以持久存储用便于取用的 JSON。引擎装载形态（`.lng`，XOR **0x88**，与官方 zh-CN 同格式）+ `NameTable.txt` 只在需要给引擎试装时临时派生：

```
python script/build_fan_translations.py --emit-lng [--lng-out <临时目录>]
```

**装载形态不留档**：引擎要的那份 `.lng` 在构建时从主产物现做（`tool/fancn.load_texts` → `tool/lng.encode_lng`，XOR 0x88）并直接封进交付归档，仓库里**不保留第二份文本留档**。留档与主产物分属两次重建，会静默落后且没有断言报警——按留档口径实测过一次：93 个脚本、2,426 个条目停在旧一波文本上（漏译补译、`♪` 还原、软换行缩进全在其中），而同口径现做与旧留档**逐字节相同**，所以取消留档是纯消歧、不改任何结果。`--emit-lng` 只作临时给引擎试装的出口，输出目录视为可丢弃；复检链一律读 `resource/fan_cn/`（经 `tool/fancn.py`）。

### 6.1 lng 条目索引机制（对官方 zh-CN 全量对账实测）

- 条目按 `\x14` 指令的 `idx` 字段索引；**条目总数 = max(对白 idx ∪ 菜单 `\x0f` 选项 id ∪ FLAG_CHECK id) + 1**，95 个官方 lng 中 93 个严格成立，2 个例外是官方文件自身尾部残留（见 lessons-learned §11）。
- 对白条目**含 `%K`/`%P` 标记**；菜单选项标签写入其 `id` 槽位、**不带**标记；对白 idx 的空洞允许存在；角色名 `\x15` 标记**不进 lng**（走 NameTable.txt，格式 `%LC<名>\t<显示名>\r\n`、UTF-16LE 明文）。
- 说话人标记是**独立于对白 idx 的原始行**（pairing 里 `kind=='name'`、`idx` 为 `None`），本项目按 idx 出包时既不重排也不改写它们，只显示名经 `NameTable` 的键值映射换名。因此"某段对话的上屏名字看起来不对"要先核对**日文原脚本自带的 `%LC`** 是否真的与台词人称矛盾，才对账译名。实测一例：`AGE_006` idx860–905（碧与扬羽的电话段）曾被通读评审怀疑 `%LC` 错标，逐条比对标记与第一人称（`俺が引っ越した後` 前为 `%LC碧`、`誰に、そのこと聞いたの？` 前为 `%LCあげは`——是扬羽反问碧从谁听来的）后确认**原脚本无错标**，不属缺陷、不做处理。
- FLAG_CHECK 的 id 与对白/菜单共用同一索引空间，实测不产生额外槽位。

### 6.2 结构化行解析（取代 §1.2 正则）

`\x14 <idx:u16> <flag:u16=0> <speaker\0> <文本>(%K%P|%K|%P) \0`：`flag≠0` 或文本含 NUL 的是 `LAYER_ORDER` 等二进制块的巧合命中，一律排除；speaker 实测仅 `char`（对白）与空（清屏行，文本恰为 `%P`）两种；空 speaker 行按官方形态填 `%P`。

### 6.3 民汉表的真实结构：位置式逐行 dump

民汉表（`AdvPatch.dll` 的 PE 资源 `PAK/#101`）**不是键值映射，而是按原版脚本出场顺序逐行倾泻的位置式队列**：87,342 个 `TextStruct{int32 crc32; wchar_t str[126]}`（步长 256 字节），条目序 = 发行时那份脚本集的行序，键值只是该行的 CRC32。

**运行时查表语义（复刻 + 实测确认）**：dll 用**一个全局游标**做"最近匹配"——在同一 CRC32 的若干候选里按游标位置取下一个；**任何一次未命中都会让游标复位**，其后所有行都从表头重新匹配，于是同一句译文被连续重复输出。这就是玩家反馈的"复读"的机制成因：它不是个别条目错值，而是位置游标一旦失步就成片复发。原版与 Steam 版脚本行序存在差异，加之表内本身缺行，失步不可避免。

**本项目从构造上消除该失效模式**：产物是按 idx 直接索引的逐脚本 JSON（§6.1），装载侧不做任何模糊/最近匹配，也就不存在游标复位。对应地，"逐条键值对齐"的旧做法（按 CRC32 找译文）已废弃，改由位置对齐（LIS 锚定 + 局部 Needleman-Wunsch，见 §7.1），错位的窗口被逐条检出并就地纠正。

**运行时验证（附加活体进程实测）**：`AdvPatch.dll` 经 `.newimp` 强制导入链加载（基址 0x70010000）；译文表在内存中存两份——堆上 `TextStruct[87342]`（每条 4 字节 CRC32 + `wchar_t[126]`，步长 256 字节，堆基址十进制 41,353,232）与 DLL 映像内的 PAK 资源本体（模块偏移 0x39468 起）。用特征串命中地址做"地址→条目号"反算（注意调试器插件打印地址为**十进制带 `0x` 前缀**，按十六进制解析会整体算错基址），全部探测点（语料行 1/3、小计数串全序列、大计数串头部序列）与 `extracted_text.jsonl` 行序**逐一吻合**——本节位置式表序即发行 DLL 内的真实表序。IDA 侧另确认 `sub_490B20` 对整行做 SJIS→UTF-16 转换后直接送显，exe 内不存在 `%K`/`%P` 字面量，`%` 与 `{` 都参与查表键计算。

## 7. 缺陷纠正流水线 ✅ 已验证

玩家反馈的五类缺陷（复读、译名不统一、繁简混合、漏翻、译校批注残留）不靠一次性人工编辑，而是固化为"对齐 → 两层改写 → 门禁出包 → 复检"的可复跑流水线。

流水线输入一律在 `resource/corpus/`：日文底稿 `jp/`、民汉旧提取 `zh/`、行对齐 `pairing.jsonl`、语境改动表 `review_fixes.jsonl`（每行 `from` 字段记录它来自哪一层，本表即语境改动的唯一终态）。切批阅读稿、机检明细、交付凭证等过程稿一律留在 `tmp/`，不作为输入。

新一轮语境改动的做法：按槽位增量并入 `review_fixes.jsonl`；`script/merge_fixes.py` 的全表重建在源层缺失时拒写，以免把已有 3,526 槽洗空。

### 7.1 位置对齐（`script/align_corpus.py`）

底稿 A = 原版脚本抽出的 87,355 条文本行，底稿 B = 民汉表 87,342 条。先在 crc 唯一的位置上求 LIS 作为锚，再在锚间做局部 Needleman-Wunsch，得到逐行对应关系。产物落 `resource/corpus/pairing.jsonl`，每行带 `kind`（dlg/name/menu/flag/ctrl）与 `src` 溯源标记：

- `positional` 87,311（位置对齐直取）、`crc-tail` 24、`ctrl` 18（`%P` 清屏行）、`need-translate` 2（表内确实没有，就地补译）；B 侧剩余 7 行为多出行（原版删减所致），不进入产物。
- 台词顺序由 idx 锁定，对齐只在同脚本内做，绝不跨脚本搬运。

### 7.2 两层改写

| 层 | 载体 | 性质 |
| --- | --- | --- |
| 机械层 | `tool/textfix.normalize()` | 零判断、每次构建全量执行、幂等 |
| 语境层 | `resource/corpus/review_fixes.jsonl` | 逐槽位记录，`from` 标来源层；本表即改动的唯一终态 |

语境改动的合成规则：并发评审 subagent 的提案按同槽位多数写法胜出（分歧写 `tmp/fix_conflicts.md`），人工裁决层按文件名顺序**无条件覆盖**提案；`script/merge_fixes.py` 按这套规则从零重建整表，新一轮改动则按槽位增量并入。改动表每行的 `from` 记录来源层，3,526 槽的实测分布：`pin_zsweep` **1,598**（全量逐行通读的落地层，最后生效）、`pin_senpai` 433（称谓裁决）、`pin_glossp` 161（拟声括注批次）、`pin_notes` 106（批注删除）、`pin_zsem` 94（逐行人工语义终审）、`pin_symbol` 65（被 GBK 吃掉的符号）、`pin_audit` 32（风险区语义审计）、`pin_variants` 31（同槽位多写法与低把握复核）、`pin_defects` 27（玩家点名缺陷就地翻译）、`pin_kana` 10（假名残留）、`pin_terms` 7（机械词表会读错的未翻日文词）、`pin_shift` 7（译文列整体错位搬回）、`pin_spotread` 6（抽读）、`pin_role` 6（职务/亲属词与昵称称谓混写）、`pin_dish` 2，以及 `from` 落在提案层的 **941** 槽（`fix_00`–`fix_07` 各批的多数写法，其中 2 槽同时记 `fix_missing`）。表按槽位存一行、`from` 只记**最终生效层**：同一槽位被后层再改写时不再挂前层名，所以各批次"落地 N 行"的读数会大于该层在表内的现存槽数。这张表**不可再由脚本重算**——它是语境改动的唯一副本。

`merge_fixes` 报的 `conflicts` 是"同一槽位存在多种提案写法"的计数，**不等于待裁决**：报告 `tmp/fix_conflicts.md` 里每条都标了是否已被 pin 层定稿。5 处分歧全部为 `[已 pin 裁决]`（如 `AGE_007` idx855、`YOR_004` idx411），因此 `conflicts 5` 是稳定状态而非缺陷；只有出现**未标记**的条目才需要人工补 pin。

`merge_fixes` 对提案/pin 只拒三类：空串、残留假名、与日文整行相同。其中假名判定会**先剔除 `ー` 与 `・`**——这两个字符落在假名 Unicode 区间内，但机械层 `PUNCT_MAP` 会把它们换成 `—`/`·`，若按区间一刀切，含延长音的整行裁决（`「也是呢ー♪」`）会被误判成"未译"而丢弃。门禁侧（G2）判的是归一后的成品，不受此豁免影响。

**批注判定批次的实测结果**：238 行逐槽位判定 → DELETE 119 / KEEP 118 / 拒绝 1。唯一被拒的是 `YOR_004` idx200——要删的批注 `（害怕Σ(⊙▽⊙"a…… ）` 里颜文字的半角 `(` 无配对，过不了"必须是完整配平圆括注"的结构校验（全语料这种形态只有 1 处，不值得放宽规则），改为人工 pin 整行。判定在落地时按"删除片段"反推校验：`cn` 与原句逐字符相等即 KEEP，否则用 `difflib` 取出被删片段，逐段要求整体是配平的圆括注、不含 `%K/%P` 与换行、内部引号成对，并核对 `%K/%P/换行/注音` 数量守恒；自报的 `removed` 只用于交叉验证。删除后的低把握 14 行由人工复核，其中 9 行因"只删括注会把拟声词删成病句"改走整行改写（`pin_variants` 的 B 组）。

**拟声词括注批次**（`script/gloss_paren.py` 检测 → `script/gen_glossp_batches.py` 切批 → 并发 subagent 提案 → 机检 → 落 `pin_glossp`）：民汉把日文拟声词写成 `（舔）（吞）（扭扭捏捏）` 这类解说式圆括注，而**日文侧根本没有圆括号**，判据是"中文圆括注数量 > 日文圆括注数量"。检测分三档：A 括号内只有拟声/语气、B 括号内是动作解说、C 日文行含破折号（省略/中断）因而允许保留少量补语。C 档最早写成"含 `――`/`―`/`、`"，结果 `（啾）、（啾）` 这种凭空造出的括注靠顿号误判成可接受；顿号不构成把解说塞进括注的理由，C 档收紧为**只认破折号**后目标集定为 **A 91 / B 71 = 162 行**（C 档 2 行允许保留）。改写判据与落地前的机检完全一致，共七条：非空、无假名、无圆括号、含汉字、不等于日文原文、`%K`/`%P` 序列逐行同构、字面 `\n` 与 `「」` 数量一致。162 行全部通过机检并入改动表，表内 `pin_glossp` 现存 **161** 槽。构建后复扫只剩 `gloss_paren total 2 A 0 B 0 C 2`（两处为日文自身带破折号的补语）。其中"含汉字"与"不等于日文"两条对**日文自身既无汉字也无假名**的纯符号行豁免（`「～～♪」` 是记谱，没有可译内容，强行加字反而是添加）。

机检只保证结构，不保证用词与日文相符，因此再加两道取证：一道按 (同日文整行不同中文) / (同日文整行出现在目标集外) / (同假名词跨脚本分歧) 扫分歧，一道导出目标槽位 ±5 行的日文、原译、成品对照。**这两道只作线索，不作改写依据**：同一个日文假名词在不同行取不同中文（`れろ` 同段既作「咧咯」又作「舔舔」，`ぎゅっ`／`ぎゅー` 普遍译作「啾」与 `ちゅ→啾` 撞车）属译者的行文变化，读者按上下文能分辨，不算缺陷；强行统一等于重写民间汉化的行文。因此逐行改写只在**该行自身**有硬伤时才做——残留圆括注、被剥成纯标点（等于漏翻）、残留假名或拉丁。曾用一致性判据攒出的 **43 行**跨行统一改写已全部撤回。

**按日文改判的 3 处**（残量 B 档按取模切 4 份交并发改写，槽位互不相交）：不能一律沿用括注里原有的动作词，要对着日文重判。`CO1_009` idx264「んしょ、んしょ」是使劲时的吆喝声（语料在 `AMA_005`/`AMA_010`/`CO2_004`/`KOT_004` 均译「嘿咻」），不能沿用括注里的动作词「涂抹」；`AMA_004` idx928「ひっく」是抽泣声，同段 idx922 已译「呜、呜呜」，单字「吸」会被读成吸气；`CO1_019` idx481「ため息をつく」是叹气，语料写成「吸了口气」属反义错译，删括注时一并改回。

**符号丢失批次（GBK 码页）**（落 `pin_symbol`）：民汉表里有一批句子中间出现 `？`，既不是疑问也配不上下文。判据不是猜测而是**码页指纹**：`♪`(U+266A)、`・`(U+30FB)、`〜`(U+301C) 在 gb2312/gbk 里编码失败，在 cp932/shift_jis/euc_jp 里正常；而 `「」『』～—…、。？` 在 GBK 里都能编码——正好对应"这三类符号在部分批次里整体消失、钩括与省略号完好"。受影响的是 **17 个脚本、87 行、136 个 `?` 字符（78 个可写槽位）**，且**同一批脚本内中文 `♪` 计数为 0**，未受影响脚本约 4 次/千行，说明丢失是按批次发生的局部事故，不是全表口径。交叉对照还有一条反证：日文侧含 `？` 的行有 6,911 行，其中 6,803 行中文就用全角 `？`，半角 `?` 在语料里不承担疑问功能，因此成品里出现半角 `?`（`tool/textfix.py` 会把 `?` 全角化，于是变成假问号）必然是符号被吃掉的痕迹。日文 `♪` 的 381 行里，中文保留 `♪` 315 行、写成 `?` 39 行、直接丢弃 27 行。处置分四档：**R1** 中文 `?` 个数 == 日文 `♪` 个数 → 逐个还原 `♪`；**R2** 日文 1 个 `♪` 而中文 2 个 `?` → `??`还原为 `～♪`、余下还原为 `♪`；**M** 29 行逐行人工判定（成对引述符 `〜…〜`、丢 `・` 的店名 `カフェ・フラッグス`、`ランウェイ・イズ・クリア` 这类 `・` 分词的西文短语、拖音 `ー`）；**SKIP** 11 行成品本就无假问号（真问号，或 ruby 读音 `{正文:・・}` 已被 `strip_ruby` 整块丢弃）。规则与人工合计 67 槽，落地时自带两条断言：未覆盖槽位必须为空、修复后仍含 `?` 的槽位必须为空。改动表 `pin_symbol` 现存 **65** 槽（另 2 槽的终值由后层改写）。构建后复检产物正文半角 `?` **0 处**。

**逐行语义终审批次**（`pin_zsem`，94 槽）：机器指标全绿之后，风险区脚本仍要靠人逐行读日文才能发现错译。取样方式是 `script/slot_ctx.py` 按 `SCRIPT:IDX` 导出日文/原译/上下文，再由并发评审 subagent 逐脚本通读。四类硬伤：**反义错译**（`CO1_019` idx481「ため息をつく」叹气→原译"吸了口气"；`SL_AMA_001` idx487「入れられながらだと」"一边被插入的话"→原译"虽然不能插进去"，把进行时写成了否定）、**漏译**（`SL_AMA_001` idx481「甘噛みする」轻咬→"甜甜地轻语"）、**同音/形近错字造成的病句**（`黏膜`→"年末"、`涵盖`→"网络在内"、`盛り込まれている`→"乘载"、`哈啊`→"蛤蛤"）、**语序与逻辑颠倒**（`SL_AMA_001` idx100/101：日文是"（我）邀请了易鸟她们，结果被拒绝了"，原译写成"易鸟她们也邀请了我""但是我拒绝了"）。这一层同样**不做跨行统一**：只改本行自身与日文不符的地方。命名取 `z` 前缀让它排在所有 pin 层最后，避免 `pin_senpai`/`pin_variants` 的 RAW 派生写法把它覆盖回去。

**全量逐行通读**：风险区终审只覆盖了十几个脚本，其余脚本的错译只有逐行读日文才暴露。工序是按脚本顺序切批（CHUNK=300 槽位，跳过已通读过的 13 个脚本，得 **215 个批次 / 49,613 个槽位**）→ 导出「日文 / 成品」对照的阅读稿 → 并发评审 subagent 逐行读日文提案 → 机检闸门 → 通过项按槽位并入改动表（`from: pin_zsweep`）。阅读稿的 `C:` 列直接取自成品 JSON，所以**每次重建产物都必须重切阅读稿**，否则评审对着旧译文提案。评审判据与交付格式固化在 `doc/sem-review-protocol.md`：只报该行自身的六类硬伤（meaning/omission/name/number/typo/untranslated），拟声词与语气词的多种写法、敬称风格、可通的近义意译、跨行统一诉求一律不报；每条提案必须带**从日文原样连续复制的 `quote`**。

通读的机检闸门是反幻觉闸门，除结构四条（`%K`/`%P` 序列、字面 `\n` 个数、「」数量、不新增括注）与"无假名/含汉字/不照抄日文"外，另有两道专门针对"subagent 凭印象编提案"：断言 `idx` 确实在该批次阅读稿里（`idx-not-in-batch`），断言 `quote` 逐字出现在该行日文里（`quote-not-in-jp`）。落地后还要给 **no-change 判据开豁免**——判据基线是成品，而成品重建后已含提案文本，不豁免会把已落地的 77 条全部误判成"与现文无差异"而拒掉。

**几条口径**（来自逐轮通读，均为稳定结论）：

- **单薄度判据可作复派依据**：被点名的批次复派后读数显著回升——「低于全语料中位数一半」实测就等于没读够，而不是那批本来就干净。
- **跨语料分布机检才是发现混写的工具**：评审只看得见自己那 300 槽，单站混写必须靠 `name_form_scan` / `nickname_scan` / `term_gap` 的分布读数兜底，并**在机械层一次清零**（而不是攒成逐槽 pin）。
- **反幻觉断言拒的是抄写，不是判断**：`quote` 抄错被 `quote-not-in-jp` 拒收时，补全 `quote` 即可，不必回退译文。
- **机检的结构约束同样约束主审**：主审改写也可能丢整对 `「」` 或多加一个字面 `\n`，被 `bracket-mismatch` / `softbreak-mismatch` 拦下。
- **评审提案与机械层规则重复时不必撤提案**：后层覆盖同值不产生漂移。
- **定字类裁决要改「生效层」**：只写 `pin_variants` 不够——下游 `pin_zsweep` 若有沿用旧写法的条目会把它覆盖回去；落地后用**分布机检**复验「少数写法归零」，而不是检查 pin 文件是否含该槽位。

### 7.3 机械层规则族（`tool/textfix.py`）

1. **工作批注剥除**：`【润色：…】`、`（注：…）`、行尾 `*注：…`（到引擎标记前）与点名的少数无关键词批注。
2. **引擎注音剥除**：`{正文:读音}` 只留正文；日文假名括注（`（セッカン）` 之类）整块删除。
3. **假名残留清理**：孤立促音/拨音与单字假名（半译残留）删除；多字假名串属整句未译，只报不改，留给语境层。**副作用必须复检**：整行只是拟声词时（`ズビシッ！`），剥完就剩 `！！`——非空、无假名，门禁拦不住。这类行由 `script/nohan_scan.py` 检出（档 A：日文侧有 3 个以上假名/汉字实词、中文侧剥掉标点后什么都不剩），交语境层按日文改写。
4. **译名统一**：多数形式胜出（蝶羽→扬羽、加奈子→佳奈子、晨风云→阵晨风云…），依据是 `tmp/term_auto.py` 的差分 n-gram 富集度。
5. **繁简与日式字形**：`LCMapStringW(2052, LCMAP_SIMPLIFIED_CHINESE)` 逐字转换，再补 `GLYPH_MAP`。判定方法不是手写清单，而是**用 GB2312 编码可行性反查**：凡简中标准收不到的字逐一点名（`script/gb2312_scan.py`，产物口径现读 **19 字 / 1,477 行次**，全部为保留字——日式字形一经进映射表就不再出现在这个读数里），再逐字分档——简中有对应字形的日式新字体进映射表（`亜瀬戸恵蛍変効対殻姉亀妬爲臓様搾晩徳於`+`荘﨑収処図転労曽毎辺姫`），人名生僻字（`瑠`1130、`柾`149）与中文拟声（`呣伮呯嗞唦囧丼瘆蹡齁窸窣唞`）保留，需要整句改写的（`畳`）留给语境层——单字替换会得到无意义的"1叠"。**但简转会留半成品**：LCMap 把日式 U+9EBC 只转到繁体 U+9EBD（`麼`）就停，而 `麼` 本身在 GB2312 内，所以 `gb2312_scan` 这类"编码可行性反查"结构上看不见它（实测成品 36 站带繁体尾巴、复检全绿）——这类只能靠 `GLYPH_MAP` 逐字收尾，并把它写进 `jp_glyph_scan.JP_ONLY` 当归零断言。**还有一条层序约束**：`normalize()` 里 `TERM_FIX` 先于 `to_simplified`/`GLYPH_MAP` 执行，同一条中文词表规则对日文写法（`恵风学院`）不生效，必须单列一条；新增词表规则一律用 `normalize()` 探针按**码点**（`ascii()`）验证各种写法是否都收敛，不能靠肉眼看渲染结果。
6. **称谓按性别落地**：`名字+前辈` 依角色性别改写作学姐/学长（语料多数形式：天音学姐 515 vs 天音前辈 222），带停顿的独立呼语不动。
7. **句读缺陷**：`。。`/`，。`/`，，`/`、、` 折叠，汉字后的半角逗号转全角。
8. **货币单位**：数字后的 `圆`/`日圆`/`日元` 统一为语料多数写法 `円`（限定左侧是数字，不动"欧元"等其他货币）。
9. **日文排版残留**：全角数字与全角拉丁字母 NFKC 折叠为半角（实测 92 行，且同句全半角混用）、全角 `％`→`%`（右侧是 `K`/`P` 时不折叠，以免凭空造出引擎标记）、数字之间的句号改回小数点、残留拉丁单位 `m`→`米`。
10. **未翻的日文词**：`寮母`→`管理员`（10 行）、裸 `寮`→`宿舍`（6 行）、`部室`→`活动室`（5 行）。依据是同槽位三方对照（`AMA_003` idx469 日文「女子寮の寮母」→官方"女生宿舍的管理员"、`KOT_007` idx695 クラブハウス→官方"社团活动室"），且语料自身也写作"女子宿舍/部团活动室"。表序上必须排在 `オンボロ寮→破旧宿舍` 之后，否则裸 `寮` 会先把该词条拆坏。
11. **日文半角钩括**：`｢｣`→`「」`（8 行；官方 zh-CN 全程只用 `「」`），其中一行的 `｢资源」` 半全角混配随归一自然配平。
12. **同音错字（限定语境）**：日文叹气/笑声 `ハァ`、`はは` 被写成"蛤"的（22 槽）改回"哈"，负向断言 `蛤(?![蟆蜊蚧])` 保住"蛤蟆/蛤蜊"这类正字；报告动词 `说道/答道/问道/嘟囔道/吼道…` 被写成"…到"的改回"道"，用后接句读的前视断言限定，不动"看到/找到"这类正常补语。这类规则放在机械层而不是 pin 层：`TERM_FIX_RE` 在所有 pin 层之后统一执行，写进 pin 反而会被上游层的 RAW 派生写法按文件名顺序覆盖回去（先前试过 `pin_ge`，因排序在 `pin_senpai`/`pin_notes` 之前而失效）。
13. **未翻的日文词「部活」**：`部活(?!动)`→`社团活动`（37 槽）。必须带负向断言：语料里 `俱乐部活动`、`滑翔部活动`、`腰部活动` 等 6 处的 `部` 与 `活动` 本不相邻，无断言的一刀切会把它们改成"俱乐部社团活动"。断言挡不住的 6 处真·社团义（`ASA_001` idx706 等）改写后中文会读歪，交给 `pin_terms` 逐槽处理，其中 `ASA_005` idx362 还要顺带把 `途中`→`中途`、`CO1_002` idx77 的 `通学路`→`上学路`。
14. **专名形近错字与少数写法**：`佳柰子`→`佳奈子`（6 槽，柰/奈 形近）、`亚沙`→`亚纱`（2 槽，两处的日文侧都写作 `亜紗`）、`杨羽`→`扬羽`（11 站，`あげは` 其余 2,183 站都作「扬羽」）、`航海日志`→`航行日志`（2 站，滑翔机不航海）。放在 `TERM_FIX` 而不是 pin 层，且 `亚沙` 必须紧跟 `亜紗→亚纱` 之后——它要在 `TITLE_FEMALE` 之前完成，否则"亚沙前辈"会先被称谓规则改写成"亚沙学姐"，错字就漏下。凡是"跨语料只有少数几站写错"的字形类事故都走这一条通道（一次清零 + 复检归零），单站且需要读日文的才进 `pin_defects`。
15. **软换行后的半角缩进**：`\n` 之后跟半角空格（330 行）折叠成全角 `　`。替换体必须写成 `lambda`：字符串形式的 `'\\n　'` 会被 `re` 还原成真实换行，把一行拆成两行，破坏引擎的换行计数。
16. **说话名不走机械层**：`NAME_FIX` 的**值**是直接写进 `NameTable` 的显示名，不经过 `normalize()`，因此第 9 条的全角折叠、第 5 条的繁简转换对说话名一律无效——值必须就地写成简体半角（`女子Ｂ`→`女子B`、`１年生女子Ａ`→`一年级女同学A` 等 6 条）。**键**反过来必须保持日文全形（`%LC女の子Ｂ` 是查表键，改键等于查不到），这是"键用日文形态、值用中文形态"的不对称约束。
17. **出包期三步（不在 `normalize()` 内，统一由 `emit()` 串起）**：`drop_dangling_break(jp, cn)` 只在**中文软换行数多于日文**时出手，删掉行尾那一个不承载正文的 `\n`——正则的尾巴必须写成 `(?:%[KP])*$`，只写 `%[KP]*$` 时 `%` 与 `K` 被当成两个独立字符、一个都匹配不到（干跑读数 `dangling 0` 就是这么来的）。**句内的多出的换行不动**：民汉在长句里自己断的 7 处节奏换行属行文选择，不是缺陷。`align_terminator(jp, cn)` 令行尾 `%K`/`%P` 组合与日文严格一致（民汉表把 `%K` 行按 `%K%P` 收录，实测命中 0 行）；`balance_brackets(cn, jp)` 只在该行自身 `「`/`」` 数量不等时出手——**日文侧本身不配对则原样保留**（镜像日文，不做无依据补全），中文多 `「` 且日文无钩括则删孤立 `「`，否则在行尾标记串之前补 `」`；中文多 `」` 且行首即 `」` 则补 `「`，其余删重复闭引号。引号配平命中 16 行（4 行按日文豁免）。三步的命中数经 `emit(..., stat)` 计入 manifest。
18. **句读误敲与半角括号**：`ASCII_PUNCT` 补 `(`→`（`、`)`→`）` 两个键（成品 2 站是 `H(呸）` 这类半全角混配）；`TERM_FIX_RE` 加 `(?<=[吗呢吧])》`→`？`（2 站——民汉把问号敲成了书名号后半，都收在语气词之后；其余 3 站 `《》` 逐行核对是真的书名/节目名，保留）。判定"是不是缺陷"靠的是与该行日文对照，而不是看中文里出现了什么符号：同一符号两类性质相反的站点必须分开处置。

### 7.4 构建门禁（`script/build_fan_translations.py`）

出包前逐条断言，任一不过即拒绝产物：G1 非空、G2 无假名/无注音/无批注、G3 写入-回读逐条相等、G4 `%K`/`%P` 与日文逐行同构（台词节奏不可变）、G5 行首控制标记一致、G6 `NameTable.txt` 显示列不含假名**且不含 `●` 占位残留**、G7 正文不含 `●`（民汉表里被表内地址/序号污染出来的条目，如 `●000824●●`）、G8 **中文行自身 `「`/`」` 不配对而该行日文配对**（落单引号上屏是一个孤立的半个引号）。零日文回退约束也在这一层（覆盖不足直接 RuntimeError）。

G6/G7 堵的是同一类漏洞：`●` 行既非空也不含假名，其余门禁全部放行；说话名 `%LC●小` / `%LC9●` / `%LC2●` / `%LC碧●` 靠"同一日文键的多数中文写法胜出"才没上屏，但这属运气，不能当机制，因此把判据写进门禁。

G8 与 `balance_brackets` 是一对：修平步骤解决"能自动判断怎么修"的行，门禁负责拦住此后任何一层重新引入的不配对（评审提案、pin 层改写都可能带进半个引号）。判据以日文侧是否配对为前提，所以 `AGE_006` idx897 那条丢引号的提案在落地前就被通读机检的 `bracket-mismatch` 拒掉了，而日文自身不闭合的 4 行（`ASA_001` idx854 等）在 G8 上天然豁免。

### 7.6 固定复跑顺序（幂等）

日常复跑只有出包与复检两段，输入是 `pairing.jsonl` + `review_fixes.jsonl`：

```
python script/build_fan_translations.py     # 默认只出 JSON 主产物；引擎试装才临时加 --emit-lng（输出目录不留档）
python script/verify_flow.py && python script/acceptance.py && python script/built_defects.py
python script/acceptance2.py && python script/extraction_accuracy.py
python script/count_parity.py && python script/nohan_scan.py && python script/gb2312_scan.py
python script/gloss_paren.py         # 括注残量回扫
```

语境层的**生成段**（切批出阅读稿 → 提案机检 → 落盘）只有在重新产出源层后才可复跑；新一轮通读的通过项按槽位**直接增量并入** `review_fixes.jsonl`。`script/merge_fixes.py` 按源层从零重建整表，源层缺失时拒写，不会把已有的 3,526 槽洗空。

引号与换行的整体结构核对是临时探针（可复跑的是 `tmp/struct_check.py` → `tmp/struct_check.md`；引号落地核对按当次缺陷现写，报告同样留在 `tmp/`、不入版本库），口径为：中文自身引号不配对的行数应等于日文自身就不闭合的行数（当前 4 == 4）、中文引号数 > 日文的行逐条确认为引述用法、`%K`/`%P` 与日文不同构必须为 0。这几项不进上面的固定序列，但**每次新增出包期改写步后都要重跑一次**。

以下两段的层序规则描述语境改动的**生效顺序**，新一轮并入时同样适用。

按层名排序，**最后生效的是 `pin_zsweep`（全量逐行通读）**，其前是 `pin_zsem`（风险区逐行语义终审），`pin_variants` 是它们之前可整表重写的一层：任何"上游层写歪了、下游层改不回"的情形先在 `pin_variants` 收口，语义层结论由 `z` 前缀压过全部上游层。

顺序无关性由层序保证：批注删除的结论会同步回写进层名排在 `pin_notes` 之后的各层，因此任何一层的先后都不会互相吞掉结论。

**反过来也有一条要守**：定字类裁决（专名、称谓）只写进 `pin_variants` 是**不够**的。若同一槽位在下游通读层 `pin_zsweep` 已有一条沿用旧写法的条目，下游会把定字覆盖回旧写法，而改动表里 `from: pin_variants` 那条看起来"已修"。`AGE_009` idx12 的「扬姐」就是这样残留了 1 站，靠 `nickname_scan` 的写法分布才发现（`扬姐姐 56 / 扬姐 1`）。做法二选一：直接改**生效层**那条的 `cn`，或删掉不生效的那条并写明原因；无论哪种，定字落地后都要用分布机检复验"少数写法归零"，而不是检查改动表是否包含该槽位。

### 7.7 官方与民间的用词分歧（裁决记录）

民间表译自**日文底稿**，官方 zh-CN 是**英文底稿**的独立译本，两者对同一日文词常取不同译法。本项目的原则：只统一"会造成同一人同一物两种写法"的硬伤，不整体改写民间表的译风。取证方法见 `script/three_way.py`（按文本配对，不能按 idx——官方 idx 与原版错位）。

**按官方口径统一**（理由是这些词在产物内部就同时存在两种写法，属缺陷）：

| 民间旧写 | 统一为 | 影响行数 | 依据 |
| --- | --- | --- | --- |
| `亜纱` | `亚纱` | 58 | 官方 900 次全用 `亚纱`；产物内自身也以 `亚纱`（1,216）为多数 |
| `水瀬` | `水濑` | 22 | 官方 72 次全用 `水濑` |
| `风戸` | `风户` | 6 | 官方 54 次全用 `风户` |
| `恵风` | `惠风` | 5 | 官方 54 次全用 `惠风`（校名） |
| `蛍` | `萤` | 1 | 官方 268 次全用 `萤` |
| `寮母` | `管理员` | 10 | 官方"女生宿舍的管理员"；民间把日文汉字直接抄进中文 |
| 裸 `寮` | `宿舍` | 6 | 同上（`オンボロ寮→破旧宿舍` 词条在前，不受影响） |
| `部室` | `活动室` | 5 | 官方"社团活动室"；民间侧亦写作"部团活动室" |
| `｢｣` | `「」` | 8 | 官方全程只用 `「」`，半角钩括是日文排版残留 |

**保留民间写法**（与官方不同，但民间忠于日文原文，改了会失真）：

| 民间 | 官方 | 日文原文 | 不改的理由 |
| --- | --- | --- | --- |
